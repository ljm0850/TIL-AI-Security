## 이번 주 배운 것
> 강의 및 실습에서 핵심적으로 가져가는 개념 3가지 이내

- **컨테이너의 본질과 격리·자원 모델**: Docker가 캡슐화로 "내 컴퓨터에선 되는데" 문제를 없애는 원리, cgroup 기반 자원 공유(기본은 전체 자원 접근), 이미지 레이어/빌드 컨텍스트/멀티스테이지·Distroless 같은 최적화·보안 관점까지. 이미지 크기 병목이 내 코드가 아니라 베이스 이미지에 있다는 걸 `docker history`로 직접 확인한 게 컸다.
- **K8s의 선언적 자동화 모델**: "원하는 상태만 선언하면 현재 상태와 계속 대조해 일치시킨다"는 핵심 철학과, 그 위에서 돌아가는 컨트롤 플레인/워커 노드 구조, ReplicaSet(개수 유지)→Deployment(롤링 업데이트/롤백)→Pod의 3층 추상화, 그리고 Service가 가변 IP 문제를 라벨 셀렉터 + 고정 엔드포인트로 해결하는 흐름.
- **상태 영속성과 네트워크 경계**: 컨테이너 데이터가 라이프사이클에 종속된다는 것(볼륨의 필요성), 그리고 기본 브리지→사용자 정의 네트워크→K8s Service로 이어지는 "이름 기반 통신(서비스 디스커버리)"의 계보. 같은 문제(이름으로 안정적으로 서로 찾기)가 계층을 바꿔가며 반복해서 등장했다.

## 이번 주 만든 것 / 기여한 것
> 실습 결과물, 팀 활동 기여 등 구체적인 산출물

- Express 앱을 직접 작성해 Dockerfile로 이미지화하고, DockerHub에 push한 뒤 K8s 클러스터에서 팟으로 배포하는 전체 파이프라인(로컬 개발 → 이미지 → 레지스트리 → 배포)을 완주.
- Color API + Traffic Generator를 만들어, 팟 가변 IP의 한계를 직접 실증하고 ClusterIP 서비스로 해결하는 실습을 완료. 로드 밸런싱(라운드 로빈)과 무중단(정상 팟 우회)을 로그로 눈으로 확인.
- PostgreSQL 컨테이너로 볼륨 유무에 따른 데이터 영속성 차이를 재현, Bind Mount로 컨테이너↔호스트 실시간 공유를 검증.

## 나는 지금 어떤 문제를 풀 수 있는가
> 이번 주 학습을 통해 새롭게 할 수 있게 된 것

- 내가 만든 애플리케이션을 이미지로 빌드해서 K8s 위에 올리고, Deployment로 원하는 개수를 유지하며 무중단으로 버전을 교체(롤링 업데이트)하거나 문제 시 롤백하는 구조를 잡을 수 있다.
- 팟이 죽고 IP가 바뀌어도 서비스가 라벨로 백엔드를 자동 추적하도록, IP가 아니라 서비스 이름(DNS)으로 통신하는 안정적인 내부 통신 구조를 설계할 수 있다.
- "돌아가게 만드는 것"과 "운영 가능하게 만드는 것"을 구분해서, 헬스체크·자가치유·데이터 영속성·자원 격리 같은 운영 관점을 배포 설계에 반영할 수 있다.

## 호기심 정리
> 이번 주 lectures/practice "다음에 파고들 만한 질문"을 훑고 처리한다.

- **살아있음 (A유형, 주말 진행 예정)**: 여러 대의 EC2 인스턴스에서 K8s를 운영하는 구조는 실제로 어떻게 설계되는가 — 마스터/워커 노드를 어떻게 배치·연결하는지. K8s 개념은 어느 정도 잡혔지만 "팀 프로젝트에서 실제로 어떤 구조를 잡아야 하는가"의 청사진이 아직 안 그려져서, 주말에 직접 구조를 그려보며 정리할 계획. (실제로 그려보면 deep-dive 승격, 못 하면 다음 회고에서 닫음)
- **닫음(만료)**: Distroless 셸 없는 디버깅(7/8 등록) — 관심은 있었으나 K8s 소화가 우선이라 이번 주엔 못 팜. 미련 없이 닫음. LL-HLS(이전 주부터 유지)도 이번 주 DevOps 집중으로 손대지 못했으나, 관심 자체는 남아있어 장기 후보로만 보류.

## 아직 부족한 것

- K8s 개념은 한 바퀴 돌았지만, 이걸 **실제 팀 프로젝트 아키텍처로 번역하는 감각**이 아직 부족하다. 어떤 서비스를 몇 개의 팟으로, 어떤 서비스 타입으로, 어떤 노드 구조 위에 올릴지 스스로 청사진을 그리는 단계까지는 못 갔다. (그래서 주말 정리가 필요함)
- 진도가 빨라서 Docker 이미지 최적화(멀티스테이지·Distroless)나 K8s의 세부 오브젝트(ConfigMap/Secret, resources requests/limits 등)는 개념만 스치고 깊이 파지는 못했다. 하중이 큰 부분은 필요할 때 다시 파는 방식으로 갈 예정.
