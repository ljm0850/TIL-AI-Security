## 이번 주 배운 것

- **SQL — 속도와 보안의 관점으로 처음 바라봤다.** 지금까지는 ORM을 통해 DB를 별 생각 없이 다뤄왔다. 이번 주에 LIKE의 풀스캔 문제, 인덱스 구조, LPAD/RPAD의 마스킹 처리가 보안과 연결된다는 걸 처음으로 의식했다. JOIN, 서브쿼리, VIEW, GROUP BY까지 다루며 SQL을 "쿼리 작성법"이 아니라 "성능과 보안을 고려하는 설계 언어"로 보게 된 전환점이었다.
- **Streamlit — 내부용 도구로서의 포지션을 이해했다.** 바이브 코딩 시대에 Streamlit이 왜 필요한지 처음엔 의문이었는데, HTML/CSS/JS 없이 Python만으로 빠르게 데이터를 시각화하고 내부 도구를 만들어야 하는 포지션이 따로 있다는 걸 알게 됐다.
- **기획은 추상화 → 정의의 과정이다.** 발주/수주 프로젝트를 통해 막연한 문제를 페르소나 → HMW → MVP로 좁혀가는 과정을 직접 경험했다. 강의에서 나온 "문제 → 추상화 → 정의" 흐름이 기획 프로세스와 정확히 겹쳤다.

## 나는 지금 어떤 문제를 풀 수 있는가

- SQL에서 SELECT, WHERE, GROUP BY, HAVING, ORDER BY의 실행 순서를 이해하고 의도한 쿼리를 작성할 수 있다
- JOIN, 서브쿼리, VIEW를 활용해 여러 테이블에 걸친 데이터를 조합하고 재사용 가능한 쿼리를 만들 수 있다
- LIKE, IN, BETWEEN 등 필터링 도구의 성능 트레이드오프를 인식하고 선택할 수 있다
- Streamlit으로 데이터 시각화 대시보드와 AI 챗봇 UI를 구현하고 배포할 수 있다
- 인터페이스 문서를 먼저 작성하고 팀원과 병렬로 개발하는 협업 방식을 실행할 수 있다
- 페르소나 단일화 결정처럼 MVP 범위를 좁히는 기획 판단을 내릴 수 있다

## 이번 주를 돌아보며

이번 주 내내 마음속에 **조급함**이 있었다. 강의와 실습에 충실히 참여하면서 이를 내 것으로 녹여낼지, 아니면 토이프로젝트에 더 많은 시간을 투자할지 자꾸 후자가 신경 쓰였다.

바이브 코딩을 지켜보면서 떠오른 생각도 비슷한 맥락이었다. 같은 바이브 코딩이어도 기본 지식이 있는 사람과 없는 사람의 결과물이 달랐다. 빠르게 만들고 싶은 욕심과, 제대로 이해하고 싶은 마음이 충돌하는 한 주였다.

SQL을 배우면서 SSAFY 팀프로젝트 때 `SELECT *`로 모든 값을 던져줬던 API, 타이핑할 때마다 API를 호출했던 검색 기능이 떠올랐다. 그때는 맡은 역할인 프론트엔드에 관심이 쏠려있어 그냥 동작하면 됐는데, 이제는 그게 왜 문제였는지가 보인다. 이게 이번 주에 가장 실질적으로 성장한 지점 같다.

다음 주부터는 JAVA다. 아주 예전에 기본 문법을 한 번 훑은 정도라 낯설 수 있지만, Python·JavaScript와 비교하며 언어 설계의 철학적 차이를 들여다보는 것이 기대된다.
