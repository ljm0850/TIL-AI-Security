## 핵심 인사이트 모음

### 📅 2026-07-20

- **CI/CD가 "통과"를 판정하는 기준이 하나 늘었다.** 지난주까지의 CI/CD에서 배포 가능 여부는 "테스트가 초록불인가"였다. ML CI/CD는 여기에 "모델 성능이 임계값을 넘는가"가 붙는다. 코드는 한 줄도 안 바뀌었는데 학습 데이터가 바뀌어서 배포가 막힐 수 있다는 게, 지금까지 내가 알던 파이프라인과 가장 다른 점이다.

- **오늘 강의가 내 메모의 질문 하나를 닫아줬다.** 실습 중에 "ML 개발에서 PR 같은 걸 생각해본 적이 없다"고 적었는데, 답은 PR이 없는 게 아니라 **PR에서 리뷰하는 대상이 코드 diff만이 아니라는 것**이었다. 실습에서 PR 본문에 accuracy, threshold, 실패 재현 이력, 원복 조치를 적게 시킨 이유가 이거다. 코드 diff만 보면 "임계값 숫자 하나 바뀜"인데, 그 숫자가 배포 가능 여부를 가르는 값이다.

- **승인 게이트는 절차 통제가 아니라 자격증명 노출 시점 통제다.** GitHub Environment에 승인자를 걸면 사람이 확인하고 넘어간다 — 여기까지는 그냥 결재 라인이다. 그런데 AWS Secrets이 production Environment에 묶여 있으면, 승인 전 job은 **비밀 값을 읽지 못한다**. 승인 게이트가 credential이 러너 메모리에 올라오는 시점 자체를 뒤로 미루는 경계선이 된다.

- **검증한 모델과 배포한 모델이 같은 물건이라는 보장이 지금 구성엔 없다.** `test_model_quality.py`는 테스트 시점에 `train.train()`을 다시 돌려서 정확도를 잰다. 그런데 실제로 배포되는 모델은 Docker 빌드 단계에서 **또 한 번 학습된** 별개의 결과물이다. iris + 로지스틱 회귀라 결정적이어서 지금은 두 값이 같지만, 시드가 없거나 비결정적인 학습이면 "통과시킨 모델"과 "배포된 모델"이 다른 파일이 된다. ch03.2에서 MLflow가 실행별 아티팩트를 등록해서 관리하는 이유가 여기에 있다고 이해했다.

- **게이트의 기준값이 게이트와 같은 권한 아래 있으면 그건 게이트가 아니다.** 실습에서 임계값을 `1.0 ↔ 0.9`로 바꿔가며 배포 차단과 통과를 재현했는데, 뒤집어 말하면 워크플로 파일을 수정할 수 있는 사람은 배포 게이트를 언제든 무력화할 수 있다는 뜻이다. 

- **헬스체크가 모델 로딩까지 확인한다는 게 지난주 삽질과 정확히 이어졌다.** 컨테이너 프로세스가 살아있어도 모델 파일을 못 읽었으면 요청 받을 준비가 된 상태가 아니다. 지난주 ALB 헬스체크 타임아웃 때 "로그는 기동됐다까지만 알려준다"고 정리했던 것의 다음 단계다 — 이번엔 아예 헬스체크 자체에 "준비됨"의 정의를 넣는다.

- **로깅 원칙에 대한 답의 일부도 오늘 나왔다.** Workflow 로그는 Secrets 값을 자동 마스킹하지만, 값을 가공해서 출력하면 마스킹이 풀린다. 로그를 "찍는 것"과 "찍어도 되는 것"이 다르다는 뜻이고, 로그가 감사 자산인 동시에 유출 표면이기도 하다

## 1. 모델 서빙과 추론 API

### 핵심 개념

- **서빙(Serving)**: 학습된 모델을 서버에서 실행하고, 외부 요청에 예측 결과를 돌려주는 API로 만드는 작업.
- **추론(Inference)**: 학습 끝난 모델에 새 입력을 넣어 결과를 계산. 학습과 달리 모델 내부 값은 바뀌지 않는다.
- **추론 API**: 추론 기능을 HTTP로 노출한 인터페이스. 실습에서는 `POST /predict`가 iris 특성 4개를 받아 품종과 확률을 반환한다.

### 상세 내용

- 모델은 학습이 끝나면 그냥 파일(`model.joblib`)이다. 노트북에서는 예측 함수를 부르면 되지만, 웹 서비스나 다른 백엔드는 이 파일을 직접 쓰기 어렵다. API가 그 사이를 끊어준다.
- **API가 모델 사용자와 모델 개발 환경을 분리한다.** 호출하는 쪽은 모델 내부 구현을 몰라도 되고, 모델을 교체하거나 재학습해도 API 규격만 유지되면 호출 코드는 안 고쳐도 된다.
  - 관심사 분리라는 점에서 ch02-3의 ECR/ECS/ALB 구조와 같은 발상이다. 바뀌는 축과 안 바뀌는 축을 갈라놓는 것.
- **모델은 시작할 때 한 번만 메모리에 읽는다.** 요청마다 파일을 읽으면 응답 시간이 늘어난다.
- **헬스체크가 모델 로딩 성공 여부까지 본다.** 프로세스 실행 ≠ 요청 처리 가능 상태.

### FastAPI 기반 iris 서빙 구조

| 파일 | 역할 |
|---|---|
| `train.py` | iris 데이터를 학습/평가로 나누고 로지스틱 회귀 학습 → 모델과 정확도를 파일로 저장 |
| `main.py` | 시작 시 `model.joblib` 로딩, `/health`·`/predict` 제공 |

```python
@app.post("/predict")
def predict(features: IrisFeatures) -> dict[str, object]:
    row = [[features.sepal_length, features.sepal_width,
            features.petal_length, features.petal_width]]
    class_index = int(model.predict(row)[0])
    probability = float(model.predict_proba(row)[0][class_index])
    return {"prediction": CLASS_NAMES[class_index], "probability": round(probability, 4)}
```

- **입력 검증(Input Validation)**: Pydantic이 요청 본문의 형식과 범위를 검사한다. 음수 꽃잎 길이처럼 물리적으로 성립하지 않는 입력은 **모델 호출 전에** 422로 거부한다.
  - 이건 편의 기능이 아니라 방어선이다. 검증 없이 들어온 이상한 값은 모델이 어떻게든 예측을 뱉는다 — 틀렸다고 말해주지 않는다. 모델은 "모르겠다"를 잘 못 하는 컴포넌트라서, 입력 경계를 앞단에서 막는 게 더 중요하다.

### 모델을 어디에 둘 것인가

| 방식 | 특징 |
|---|---|
| Docker 이미지에 포함 (실습 방식) | 빌드 중 학습을 실행해 모델을 이미지에 넣음. 이미지 태그 하나에 코드+모델이 같이 기록되어 버전 관계가 명확 |
| 외부 모델 저장소에서 다운로드 | 모델이 크거나 재학습 주기가 짧을 때 적합. MLflow 기반 분리 방식은 ch03-2 |

## 2. ML CI/CD 검증

### 핵심 개념

일반 CI/CD는 **코드가 요구한 동작을 하는가**를 본다. ML 시스템은 코드가 안 바뀌어도 학습 데이터가 바뀌면 예측 품질이 달라진다. 그래서 검증 대상에 데이터와 모델이 추가된다.

| 구분 | 일반 CI/CD | ML CI/CD |
|---|---|---|
| 검증 대상 | 코드 | 코드 + 데이터 + 모델 |
| 변경 원인 | 코드 수정 | 코드 수정, 데이터 변화, 재학습 |
| 통과 기준 | 테스트 성공, 빌드 성공 | 테스트 성공 + 모델 성능 기준 충족 |
| 산출물 | 애플리케이션 이미지 | 애플리케이션 이미지 + 모델 아티팩트 |

### 상세 내용

**검증 3분할** — 실패 원인과 확인 방법이 서로 달라서 단계를 나눠두면 실패 위치만으로 확인 범위를 줄일 수 있다.

| 검증 | 담당 | 확인하는 것 |
|---|---|---|
| 코드 검증 | `test_api.py` | API가 요청을 처리하는지, 입력 검증이 작동하는지 |
| 데이터 검증 | Pydantic (추론 입력) | 형식·범위·결측. 학습 데이터 검증은 개념 소개 수준 |
| 모델 검증 | `test_model_quality.py` | 정확도가 임계값 이상인지 |

**모델 성능 임계값 검증**

```python
THRESHOLD = float(os.environ.get("MODEL_ACCURACY_THRESHOLD", "0.9"))

def test_model_accuracy_meets_threshold() -> None:
    metrics = train.train()
    assert metrics["accuracy"] >= THRESHOLD
```

- 사람이 배포마다 지표를 눈으로 확인하면 누락이 생긴다. 기준을 테스트 코드에 숫자로 박아두면 파이프라인이 같은 기준을 매번 반복 적용한다.
- 환경 변수로 빼두면 코드 수정 없이 기준을 바꿔 실험할 수 있다. 다만 **그 편리함이 곧 우회 경로**이기도 하다는 게 위 인사이트에서 짚은 부분.

**관련 용어**

- **배포 차단(Deployment Blocking)**: 검증 실패 후 빌드·배포를 실행하지 않는 동작. GitHub Actions의 `needs`로 구성.
- **평가 데이터 분리(Train-Test Split)**: 학습에 안 쓴 데이터로 성능 측정. 같은 데이터로 학습·평가하면 점수가 높게 나와서 임계값 검증 자체가 무의미해진다.

**정확도 하나로는 부족하다**

- 특정 품종만 계속 오분류되는 문제는 전체 정확도로는 안 보인다.
- 평가 데이터와 운영 데이터의 분포가 다르면, 테스트를 통과한 모델도 운영에서 성능이 떨어진다. → 분포 변화(드리프트)는 ch04-1.
  - 이 지점이 보안 관점에서도 흥미롭다. 학습 데이터가 오염되면 코드 리뷰에는 아무것도 안 걸린다. 코드 검증이 못 잡는 걸 데이터·모델 검증이 잡는 구조라는 게 방어 계층으로 읽힌다.

## 3. 승인 게이트와 배포

### 핵심 개념

자동 검증은 정해진 규칙을 빠짐없이 반복한다. 하지만 **"지금 배포해도 되는 시점인가", "변경 공지가 필요한가"는 규칙으로 판단이 안 된다.** 그 부분을 사람이 맡는 게 승인 게이트다.

### 상세 내용

**GitHub Environments**

| 구성 요소 | 설명 |
|---|---|
| Environment | 배포 대상 환경 단위. job에 `environment: production` 지정 시 해당 환경의 Secrets·보호 규칙 적용 |
| Required reviewers | 승인 가능한 사용자 목록. Approve / Reject 선택 |
| Environment secrets | 환경별 비밀 값. **승인 전 job은 읽을 수 없다** |

**Workflow 구성 (ch03-1)**

```yaml
jobs:
  test-and-validate:       # 코드 테스트 + 모델 성능 검증
    ...
  docker-build:            # 이미지 빌드 검증 (모델 포함)
    needs: test-and-validate
  deploy:                  # 승인 게이트 통과 후 ECR Push + ECS 배포
    needs: docker-build
    environment: production
```

- 모델 성능이 임계값에 못 미치면 `test-and-validate`에서 끝나고 뒤 job은 아예 시작하지 않는다.
- **단계 분리(Job Separation)**: 실패한 job이 표시되므로 원인 확인 범위가 좁아진다.
- **검증 아티팩트**: `metrics.json`을 업로드해 배포 실행 시점에 모델 성능을 확인할 수 있게 남긴다.
- 배포 job은 ch02-3의 ECR 리포지터리, 태스크 정의 템플릿, ECS 서비스를 **그대로 재사용**한다. 인프라를 새로 만들지 않고 배포 대상만 ML 서빙 컨테이너로 바꾼다. 이미지 태그에는 `ml-` 접두사를 붙인 커밋 해시를 쓴다.

**승인 게이트의 비용**

- 승인은 배포 시간을 늘린다. 하루에 수십 번 배포하는 팀이 전부 수동 승인을 걸면 승인이 형식화된다.
- 그래서 운영 환경에는 승인, 검증 환경에는 자동 배포를 적용하는 구성이 흔하다.
  - 지난주 SG 세분화 때 느낀 것과 같은 종류의 트레이드오프다. 통제를 촘촘히 걸수록 안전해지지만, 사람이 감당 못 하는 통제는 형식만 남고 실질이 빠진다.

**두 개의 Workflow (앞으로)**

- `ml-cicd`: main 브랜치 Push마다 승인 게이트 뒤에 배포.
- `ml-deploy` (ch03-3 예정): MLflow Model Registry의 champion 별칭을 확인한 뒤 실행.
- 둘은 서로 대체하지 않는다. Actions 실행 기록의 Workflow 이름·시각으로 어느 경로로 배포됐는지 구분한다.

## 4. 배포 로그와 실패 분석

### 핵심 개념

파이프라인이 멈추면 **실패한 job → 실패한 step → 오류 메시지** 순서로 읽는다. 배포가 끝난 뒤에는 CloudWatch로 컨테이너의 모델 로딩과 요청 처리를 확인한다.

### 상세 내용

**GitHub Actions 로그 분석**

GitHub Actions는 Workflow → Job → Step 계층으로 로그를 보여준다.

1. Actions 탭에서 실패한 실행을 열고 빨간 job 확인
2. job을 열어 멈춘 step 확인
3. step 로그를 펼쳐 오류 메시지 확인 (pytest는 실패 테스트와 assert 위치를 표시)
4. 수정 커밋 push 후 재실행 확인

**실패 유형을 로그 형식으로 구분한다** — 오늘 배운 것 중 실전에서 바로 쓸 부분.

| 로그 형태 | 의미 | 조치 방향 |
|---|---|---|
| 예외(traceback) | 코드 오류 | 코드 수정 |
| assert 실패 (실제값 vs 기준값 표시) | 임계값 미달 | 모델·데이터 개선 |

- 지난주 "Request timed out은 거의 항상 네트워크 경로 문제"와 같은 종류의 판별 기준이다. **에러의 모양이 조사 범위를 정해준다.**

**CloudWatch 서비스 로그**

- 배포 성공은 컨테이너가 실행됐다는 사실만 알려준다. API가 요청을 처리하는지는 서비스 로그에서 따로 본다.
- ECS Fargate 컨테이너의 표준 출력 → 태스크 정의의 `awslogs` 드라이버 → CloudWatch Logs.
- **로그 그룹**: 로그를 모으는 단위. 태스크 정의의 `awslogs-group` 값과 이름이 일치해야 한다.
- **로그 스트림**: 컨테이너 하나가 남기는 로그 흐름. 배포로 태스크가 교체되면 새 스트림이 생긴다. → 배포 후 로그를 볼 때 옛 스트림을 보고 있진 않은지 확인해야 한다.

```bash
aws logs describe-log-groups --log-group-name-prefix /ecs
aws logs tail /ecs/devmlops-fastapi --since 10m
```

## 5. 민감 정보 관리 점검

### 핵심 개념

ML 파이프라인은 AWS 자격 증명, 데이터 접근 키 같은 민감 정보를 쓴다. **비밀 값이 코드·로그·이미지에 남지 않았는지 확인하는 작업 자체가 파이프라인 구성의 일부**다.

### 상세 내용

| 점검 대상 | 원칙 |
|---|---|
| Secrets 저장 | 코드·설정 파일이 아니라 GitHub Secrets 또는 Environment secrets |
| Workflow 로그 | Secrets는 자동 마스킹되지만 **값을 가공해 출력하면 마스킹이 풀린다.** `echo`로 찍지 않는다 |
| 커밋 전 | `.env`, 자격 증명 파일, 개인 데이터가 커밋 대상에 없는지 `git status`·`.gitignore` 확인 |
| 이미지 | 빌드 인자로 비밀을 넘기면 **레이어에 남는다.** 실행 시 환경 변수로 주입 |
| IAM | 파이프라인 역할에 필요한 권한만. ch02-3의 OIDC 역할은 ECR·ECS 권한만 사용 |

- 비밀 값이 커밋되면 Git 이력에서 지우기 어렵다. **공개 저장소에 push된 비밀은 이미 유출로 보고 폐기 후 재발급**한다. 되돌리는 게 아니라 무효화하는 게 대응이라는 점이 핵심이다.
- 이미지 레이어 얘기는 지난주 Docker 멀티스테이지에서 본 것과 이어진다. 레이어는 지운 것도 기록으로 남는다 — 최종 이미지에 파일이 없어도 중간 레이어에 있으면 있는 거다.
