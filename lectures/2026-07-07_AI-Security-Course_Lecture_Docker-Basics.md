## 핵심 인사이트 모음

### 📅 2026-07-07

- 기존 배포 방식이 "Devs가 스크립트 쓰고 → 안 돌아가고 → Ops가 고치고 → 다시 돌리고"의 무한 루프였다는 설명을 보니, 컨테이너가 왜 "캡슐화" 하나로 이 문제를 해결한다고 하는지 감이 왔다. 결국 "내 컴퓨터에선 되는데?" 문제를 이미지 단위로 통째 처리한다.
- Docker Hub는 GitHub이랑 구조가 많이 닮았다는 생각이 들었다. 로컬에서 build(커밋) → push(원격 저장소에 업로드) → 다른 환경에서 pull(clone/pull) 받는 흐름이 거의 그대로 겹친다. 다만 GitHub은 소스 코드 버전 관리, Docker Hub는 실행 가능한 이미지(빌드 완료 상태) 버전 관리라는 차이.
- Parameter(매개변수)는 값을 받는 "그릇", Argument(인자)는 그 그릇에 실제로 넘겨주는 "값"이라는 구분을 이번에 명확히 함. `docker run -d -p 8080:80 --name web_server nginx`에서 `-p`, `--name` 같은 옵션들이 각각 파라미터 역할을 하고, `8080:80`, `web_server`가 그 자리에 넘겨진 인자값이라고 보면 됨.
- 이미지가 "컨테이너의 DNA/청사진"이라는 비유, 그리고 이미지는 읽기 전용이고 컨테이너는 그걸 기반으로 실행되는 인스턴스라는 관계가 클래스-인스턴스 관계랑 비슷하게 느껴짐.

## 1. 컨테이너를 쓰는 이유 (Why Containers?)

### 핵심 개념
- 기존 배포 방식: 언어/버전/의존성마다 설치 과정이 다 다르고, 여러 앱을 한 서버에서 동시에 관리하기도 어려움
- 컨테이너의 핵심 메커니즘은 **캡슐화(Encapsulation)**: 애플리케이션 실행에 필요한 모든 의존성과 설정을 하나로 묶음

### 상세 내용
- 기존 방식의 전형적인 문제: 배포 스크립트 작성 → 작동 안 함 → 수정 → 의존성 재설치 → 반복 끝에 겨우 배포
- 컨테이너를 쓰면 내부 내용물과 무관하게 모든 컨테이너가 동일한 형태로 실행·관리됨
- 장점: 설정 단순화, 높은 이식성, 일관된 환경, 격리성, VM 대비 높은 효율성, 나은 자원 제어, 손쉬운 확장

## 2. 컨테이너 vs 가상 머신(VM)

### 핵심 개념
- VM은 OS 단위 격리, 컨테이너는 호스트 커널을 공유하는 프로세스 단위 격리

### 상세 내용

| 구분 | VM | Docker 컨테이너 |
|---|---|---|
| 격리성 | 각 VM이 자체 OS를 가진 강력한 격리 | 호스트 OS 커널 공유, 프로세스 레벨 격리 |
| 오버헤드 | 게스트 OS+가상 하드웨어 필요, 큼 | 커널 공유로 경량 |
| 이식성 | 하이퍼바이저/게스트 OS 설정에 종속, 낮음 | 플랫폼 독립적, 높음 |
| 적합한 상황 | 강력한 격리 필요, 레거시 앱, 전체 시스템 복제 테스트 | 마이크로서비스, 빠른 확장, 이식성 최우선 |

## 3. Docker Components — 실행/빌드 흐름

### 핵심 개념
- `docker run`(이미지→컨테이너 실행)과 `docker build`+`docker push`(코드→이미지→레지스트리) 두 흐름이 분리되어 있음

### 상세 내용
**이미지로부터 컨테이너 실행 (`docker run`)**

1. 사용자가 CLI에 `docker run <image>` 입력
2. REST API를 통해 Docker Host 엔드포인트로 전달
3. Docker Daemon이 로컬 이미지 캐시 확인
4. 로컬에 없으면 원격 레지스트리(Docker Hub 등)에서 이미지 레이어 pull
5. 확보된 이미지로 컨테이너 인스턴스 생성·실행

**이미지 빌드 및 푸시 (`docker build` → `docker push`)**

1. 사용자가 CLI에 `docker build` 입력
2. CLI가 Dockerfile + 빌드 컨텍스트(소스 코드, 에셋 등)를 Docker Host로 전송
3. Docker Daemon이 Dockerfile 지시어를 한 줄씩 실행하며 로컬에 이미지 빌드
4. `docker push` 명령으로 로컬 이미지를 원격 레지스트리로 업로드

## 4. Docker Images

### 핵심 개념
- 이미지는 애플리케이션 실행에 필요한 모든 요소를 캡슐화한 읽기 전용 템플릿 (컨테이너의 DNA/청사진)

### 상세 내용
- 이미지를 구성하는 5가지 레이어: 베이스 레이어(Alpine/Ubuntu 등) → 런타임 환경(Python/Node.js 등) → 라이브러리·의존성 → 애플리케이션 코드 → 설정(환경변수 등)
- 이미지 공급 출처 3가지: Docker Hub(공식 저장소), 사설 레지스트리(기업 보안용), 자체 빌드(Dockerfile로 직접 생성)

---

## 5. Container Registries

### 핵심 개념
- 이미지를 저장·공유·버전관리하는 저장소

### 상세 내용
- 레지스트리 사용의 이점: 협업(팀/커뮤니티 이미지 공유), 버전 관리(업데이트·롤백), 보안(프라이빗 저장), 자동화(CI/CD 연계)
- 유형: 공용 레지스트리(Docker Hub 등, 누구나 접근), 사설 레지스트리(민감한 이미지, 세분화된 접근 제어)

## 6. Dockerfile

### 핵심 개념
- Docker 이미지를 만들기 위한 빌드 단계를 코드로 정의한 명세서

### 상세 내용
- 기본 문법: `#` 주석, `FROM`/`RUN`/`COPY` 등 대문자 지시어(Instruction), 지시어 뒤에 오는 인자(Arguments)
- 4가지 장점:
  - 재현성: Dockerfile만 있으면 누구나 동일한 이미지 재생성 가능
  - 자동화: 수동 명령 입력 제거로 휴먼 에러 감소
  - 투명성/문서화: 빌드 과정 자체가 문서 역할
  - 최적화: 빌드 단계 전체를 제어해 보안 강화, 빌드 시간·이미지 용량 최적화
