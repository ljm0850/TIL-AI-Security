### 📅 2026-07-02

**AWS를 배우면서 과거 프로젝트 MSA 고민이 다시 연결됐다**

과거 팀 프로젝트에서 "MSA에서 DB를 나눠야 하는가, 공통 데이터는 어떻게 처리하는가"를 팀원과 이야기 나눴던 기억이 오늘 VPC와 네트워킹을 배우면서 다시 떠올랐다. 오늘 강의 중 Claude와 대화하면서 구조적으로 정리됐다 — 로드밸런서/쿠버네티스 트래픽 흐름과 MSA 데이터 관리 패턴. 상세는 deep-dive 참조.

**IaaS/PaaS/SaaS 구분 — "어디까지 내가 관리하는가"**

세 가지 서비스 모델의 차이는 결국 "어디까지 클라우드 공급자가 관리하고 어디서부터 내가 책임지는가"의 경계다. EC2는 IaaS라서 OS부터 애플리케이션까지 내가 관리한다 — 그래서 리눅스를 알아야 하는 이유가 여기서 연결된다. 리눅스를 배우는 게 "AWS에 올라간 서버를 다루기 위함"이라는 맥락이 이제야 연결됐다.

**EC2 보안 그룹 — 토이프로젝트에서 쓴 것의 구조적 이해**

토이프로젝트에서 SSH/HTTP/HTTPS 접근 IP를 제한했던 게 보안 그룹이었는데, 당시엔 그냥 설정 화면에서 따라한 수준이었다. 오늘 보니 이게 인스턴스 레벨의 방화벽이고, VPC 안에서 어떤 트래픽을 허용/거부할지 정의하는 구조다. MSA에서 회원 DB 서버를 외부에 노출하지 않으려면 — 보안 그룹으로 특정 서비스 서버의 사설 IP에서 오는 요청만 허용해야 한다.

**인스턴스 스토어 vs EBS — 휘발성의 의미**

인스턴스 스토어는 EC2 중지/종료 시 데이터가 사라진다. 어제 정리한 "환경변수는 프로세스가 죽으면 사라진다"는 휘발성 개념과 같은 패턴이 스토리지 레벨에서도 나온다 — 어디에 저장하느냐가 데이터의 생존 범위를 결정한다. 중요한 데이터는 EBS(외장 하드 개념)에 두어야 인스턴스가 재시작돼도 살아남는다.

## 1. 클라우드 컴퓨팅 개념

### On-premises vs 클라우드
- **On-premises**: 서버를 직접 구매·설치·관리. 비용·공간·인적 자원 부담이 크고, 수요 예측 실패 시 낭비 또는 부족
- **클라우드**: 필요할 때 on-demand로 IT 자원을 빌려 쓰는 방식. 초기 투자 없이 사용량만큼 비용 지불

### 서비스 모델 3종

| 모델 | 공급자 관리 | 사용자 관리 | 대표 예 |
|---|---|---|---|
| **IaaS** | 서버/스토리지/네트워킹, 가상화 | OS, 미들웨어, 런타임, 데이터, 앱 | AWS EC2 |
| **PaaS** | IaaS + OS, 미들웨어, 런타임 | 데이터, 앱 | AWS Elastic Beanstalk |
| **SaaS** | 전부 | 없음 (사용만) | Gmail, Slack |

### 클라우드 유형
- **퍼블릭 클라우드**: AWS, Microsoft Azure, GCP 등 — 공유 인프라, 인터넷으로 접근
- **프라이빗 클라우드**: 사용자 전용, on-premises 환경에 구축, 자원 소유권은 사용자

### AWS 관리 방법
- AWS 관리 콘솔 (웹 UI)
- AWS CLI (커맨드라인)
- AWS SDK (코드에서 API 호출)

|---|---|
| **EC2** | 가상 서버 제공 (IaaS) |

## 3. EC2 (Elastic Compute Cloud)

AWS 퍼블릭 클라우드에서 확장 가능한 가상 서버를 제공하는 서비스.

### AMI (Amazon Machine Image)
- OS와 소프트웨어를 구성한 상태로 제공되는 템플릿
- EC2 인스턴스를 만들 때 어떤 OS/소프트웨어 환경에서 시작할지 결정하는 기반

### EC2 스토리지

| 종류 | 특징 | 비유 |
|---|---|---|
| **인스턴스 스토어** | 빠른 I/O, EC2 중지/종료 시 데이터 소멸 | 휘발성 메모리 |
| **Amazon EBS** | EC2와 독립적으로 존재, 인스턴스 재시작에도 데이터 유지 | 외장 하드디스크 |

> 중요 데이터는 반드시 EBS에. 인스턴스 스토어는 캐시·임시 파일 등 휘발성 용도로만.

### EC2 네트워킹 — VPC

- **Amazon VPC (Virtual Private Cloud)**: AWS 퍼블릭 클라우드 안에서 논리적으로 격리된 가상 네트워크
- MSA 구성 시 서비스 간 내부 통신은 VPC 안의 **사설 IP**로 처리 가능 — 외부 인터넷에 노출하지 않고 서비스끼리만 통신
- 회원 DB처럼 외부 노출을 막아야 하는 서버는: 보안 그룹으로 특정 서비스 서버의 사설 IP 접근만 허용하는 방식으로 격리

### EC2 보안

**보안 그룹**
- 인스턴스 레벨 방화벽. 트래픽 허용/거부 규칙 정의
- 토이프로젝트에서 SSH(22)/HTTP(80)/HTTPS(443) 접근 IP를 제한했던 게 이것
- 인바운드(들어오는 트래픽) / 아웃바운드(나가는 트래픽) 별도 설정

**키 페어**
- 퍼블릭 키(AWS 보관) + 프라이빗 키(로컬 보관) 구성
- SSH 접속 시 프라이빗 키로 인증. 비밀번호 없이 접속 가능하면서 보안 유지

**EC2 Auto Scaling**
- 트래픽에 따라 인스턴스를 자동으로 추가/제거
- ALB(로드밸런서)와 조합해서 트래픽 증가 시 자동 확장, 감소 시 자동 축소

### 오늘 실습
- AWS 콘솔 계정 생성
- EC2 인스턴스 생성 (t3.micro, Ubuntu)
- 키 페어로 SSH 접속 (WSL Ubuntu 이용)
