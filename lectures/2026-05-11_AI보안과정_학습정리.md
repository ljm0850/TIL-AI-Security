## 1. AI 리터러시와 한계 이해

### 핵심 개념

- AI는 규칙을 직접 프로그래밍하는 게 아니라, 데이터에서 패턴을 학습하는 시스템
- LLM은 사실을 '이해'하는 게 아니라, 확률이 가장 높은 토큰을 순서대로 '생성'하는 구조
- 할루시네이션은 버그가 아닌 확률 기반 구조에서 오는 근본적 특성
- AI 리터러시 = 기술 이해 + 비판적 사고 + 윤리 인식 + 실무 적용

### 상세 내용

**LLM 작동 원리 — 토큰 예측**

- 텍스트를 토큰 단위로 분해 → 확률 계산 → 최적 토큰 선택 → 반복
- 예: "오늘 날씨가 ___" → 맑습니다(45%) / 흐립니다(30%) / 춥습니다(15%) 중 선택
- 출력값이 사실인지 내부적으로 검증하는 로직 없음

**트랜스포머 & 자기지도학습**

- 트랜스포머: 문장 전체 문맥을 병렬 처리 → LLM의 핵심 아키텍처
- Self-Attention: 문장 내 멀리 떨어진 단어 간 관계도 동시에 계산
- 자기지도학습: 사람이 레이블 안 달아도, 다음 단어 예측 반복으로 스스로 언어 구조 학습

**2026년 AI 기술 트렌드**

| 패러다임         | 설명                                                         |
| ---------------- | ------------------------------------------------------------ |
| **에이전틱 AI**  | 목표 부여 시 스스로 계획·실행·판단. 2026년까지 기업용 앱 약 40% 도입 전망 |
| **피지컬 AI**    | 로봇·드론·자율주행차 등 하드웨어와 결합. CES 2026 핵심 키워드 |
| **소버린 AI**    | 국가 단위 데이터 주권·기술 독립 경쟁 심화                    |
| **책임 있는 AI** | EU AI Act 등 글로벌 규제 현실화, 윤리성·안전성 제도화        |

- 기업용 AI 에이전트 시장: 2025년 15억 달러 → 2030년 418억 달러 (약 28배 성장 전망)

**AI의 구조적 한계**

| 한계                  | 설명                                                         |
| --------------------- | ------------------------------------------------------------ |
| **검증 기능 부재**    | 생성에 특화, 결과값 사실 여부를 검증하는 내부 로직 없음      |
| **할루시네이션**      | 자연스러운 문체로 잘못된 정보를 자신감 있게 생성 — 미국 변호사 가짜 판례 제출 사건, 세종대왕 맥북 던짐 사건 |
| **Knowledge Cut-off** | 특정 시점 이후 정보 모름. 학습 데이터 편향도 그대로 반영     |
| **맥락 유지 한계**    | 대화가 극도로 길어지면 초기 정보 망각, 모순 발생             |

**AI 보안 위협**

- 딥페이크: 3~5초 음성 샘플로 특정인 목소리 복제. 영국 아룹사 화상회의 사기 → 약 2,500만 달러 피해
- 프롬프트 인젝션: 악의적 프롬프트로 AI 내부 설정 조작, API 키·개인정보 탈취. 2025년 약 23억 달러 손실 추산
- 공격 자동화: 타깃 분석부터 악성코드 생성까지 AI가 전 과정 수행
- iOS 인젝션 공격: 2025년 전년 대비 741% 급증

**AI를 올바르게 쓰는 법 — 4대 원칙**

1. **출처 교차 검증**: AI 답변을 1차 자료와 반드시 대조
2. **민감 정보 입력 금지**: 개인정보·사내 기밀 등 보안 민감 정보 입력 금지
3. **정교한 프롬프트 설계**: 명확한 제약 조건 명시 ("확실하지 않으면 모른다고 답할 것" 등)
4. **Human-in-the-loop**: AI 출력물은 초안. 사람이 최종 검토·수정 후 사용

## 2. 유저 중심 문제 정의

### 핵심 개념

- 프로젝트 실패의 85%는 기술 문제가 아니라 잘못된 문제 정의에서 비롯 (스탠퍼드 d.school)
- 디자인 씽킹: 공감 → 정의 → 아이디어화 → 프로토타입 → 테스트
- 페르소나 → Pain Point → POV → HMW 흐름이 문제 정의의 핵심 프레임

### 상세 내용

**디자인 씽킹 5단계**

| 단계           | 핵심 활동                               | 주요 산출물        |
| -------------- | --------------------------------------- | ------------------ |
| **공감**       | 사용자 관찰·인터뷰, 잠재 니즈 파악      | 페르소나, 공감지도 |
| **정의**       | 수집 정보 분석, 핵심 문제를 한 문장으로 | 문제 정의문(POV)   |
| **아이디어화** | 고정관념 탈피, 다양한 해결책 발산       | 아이디어 리스트    |
| **프로토타입** | 신속 시각화·구현 (완성도보다 검증 우선) | 와이어프레임, 목업 |
| **테스트**     | 실사용자 검증, 피드백 수집, 반복 개선   | 사용자 피드백      |

**공감지도 (Empathy Map)**

| 구성 요소        | 내용                                      |
| ---------------- | ----------------------------------------- |
| **Think & Feel** | 겉으로 드러내지 않는 진짜 생각과 감정     |
| **See & Hear**   | 일상 환경, 외부 정보                      |
| **Say & Do**     | 인터뷰 발언, 실제 행동                    |
| **Pains**        | 두려움·좌절·장애물 → Pain Point 도출      |
| **Gains**        | 궁극적 욕구·목표 → Value Proposition 방향 |

**페르소나 → Pain Point → POV → HMW 흐름**

```
공감 → 페르소나 → Pain Point → POV → HMW → 사용자 여정 지도
```

- **페르소나**: 실제 사용자 조사 데이터 기반 가상 대표 사용자 프로파일. 팀 의사결정 기준 통일
- **Pain Point**: 페르소나가 돈과 시간을 기꺼이 투자해서라도 해결하고 싶은 고통 지점
- **POV 작성 공식**: `[페르소나]는 [필요/욕구]가 필요하다. 왜냐하면 [인사이트]이기 때문이다.`
- **HMW**: "어떻게 하면 우리가 [문제]를 해결할 수 있을까?" — 문제를 긍정적 도전으로 재정의

**POV 예시 비교**

|      | 예시                                                         | 평가                             |
| ---- | ------------------------------------------------------------ | -------------------------------- |
| ❌    | "사용자는 더 좋은 앱이 필요하다."                            | 너무 모호, 방향 없음             |
| ✅    | "취준생 김지수는 코딩 없이 AI 포트폴리오를 만들 방법이 필요하다. 왜냐하면 개발 경험 없이는 취업 경쟁에서 뒤처진다는 불안감을 느끼기 때문이다." | 대상·결핍·심리적 인사이트 구체적 |

**사용자 여정 지도 (User Journey Map)**

- 행동·감정·터치포인트·장벽 중심으로 전체 경험 과정 시각화
- 감정 곡선이 급격히 하락하는 지점 = 서비스 개선 최우선 순위
- 제작 도구: Figma(FigJam), Miro, Canva

## 오늘의 핵심 인사이트

- **AI는 만능이 아니라 확률 기계다**: 그럴듯한 문장을 잘 만들어낼 뿐, 사실 여부는 스스로 모른다. 이걸 이해하는 것이 AI 리터러시의 출발점.
- **할루시네이션은 고칠 수 있는 버그가 아니다**: 확률 기반 구조에서 나오는 근본적 특성. GPT-4도 Gemini도 여전히 틀린다. 항상 검증하는 습관이 필요.
- **문제 정의가 솔루션보다 먼저다**: 기술이 훌륭해도 잘못된 문제를 풀면 실패한다. 올바른 문제를 찾는 능력이 가장 중요한 역량.
- **페르소나→POV→HMW 흐름은 AI 서비스 기획에도 그대로 쓸 수 있다**: 기획 방법론인데, AI 보안 서비스를 만들 때도 똑같이 적용될 것 같다.

## 3. PRD (제품 요구사항 정의서)

### 핵심 개념

- PRD = HMW로 발산한 가능성 중 가장 효과적인 해결책을 선택해 구현 가능한 형태로 만드는 문서
- 팀 구성원 모두가 동일한 목표를 바라보게 하는 '공통 언어' 역할
- PRD 없이 시작한 프로젝트의 60%가 Scope Creep으로 실패 (Atlassian 연구)

### 상세 내용

**문서 위계**

```
MRD (시장 요구사항) → PRD (제품 요구사항) → 개발 스펙 (기술 요구사항)
```

**PRD가 필요한 이유**

- **동상이몽 방지**: 디자이너는 화면, 개발자는 로직, 기획자는 흐름을 각자 상상하면 통합 불가능한 제품 탄생
- **기회비용 최적화**: 방향 변경이 반복될수록 개발 비용·시간이 기하급수적으로 증가. 재작업(Rework) 최소화
- **의사결정 근거**: 이해관계자 설득과 합리적 의사결정의 기준점

**PRD 7대 구성요소**

| 구성요소                                         | 설명                                              |
| ------------------------------------------------ | ------------------------------------------------- |
| **배경 (Background)**                            | '왜 이것을 만드는가' — 문제와 근거 데이터         |
| **목표 및 핵심 지표 (Goals & KPI)**              | 비즈니스 목표 + 수치화된 성공 기준                |
| **범위 (Scope)**                                 | 포함되는 기능 vs 포함되지 않는 기능 명확히 구분   |
| **사용자 시나리오 (User Scenario)**              | 페르소나가 제품을 사용하는 흐름 (User Story 기반) |
| **상세 기능 요구사항 (Functional Requirements)** | 개발자·디자이너가 바로 작업 착수할 수 있는 명세   |
| **우선순위 (Priority)**                          | MoSCoW 기법으로 기능별 중요도 결정                |
| **예외 사항 및 정책 (Edge Cases & Policy)**      | 특이 케이스, 보안·운영 정책 선제적 정의           |

**User Story 작성법**

- 작성 공식: `[사용자 유형]은 [목적]을 위해 [기능/욕구]를 원한다`
- 각 스토리에는 **완료 조건 (Acceptance Criteria)** 을 반드시 추가 — "언제 이 기능을 완성으로 간주할 것인가"

**INVEST 원칙** — 좋은 User Story 검증 기준

| 원칙            | 의미                            |
| --------------- | ------------------------------- |
| **I**ndependent | 각 스토리는 서로 독립적         |
| **N**egotiable  | 세부 사항은 협의 가능           |
| **V**aluable    | 사용자에게 반드시 가치 제공     |
| **E**stimable   | 작업 규모를 추정 가능           |
| **S**mall       | 적절한 시간 내 완료 가능한 크기 |
| **T**estable    | 테스트로 검증 가능              |

## 4. MVP와 린 스타트업

### 핵심 개념

- MVP(Minimum Viable Product): 핵심 가설을 검증할 수 있는 최소한의 제품. '미완성 제품'이 아니라 '가설 검증 도구'
- 최소 기능(Minimum)보다 **실행 가능성(Viable)** 에 집중 — 고객이 실제로 쓰고 피드백을 줄 수 있는 수준이어야 함
- 린 스타트업에서는 '성공적인 런칭'보다 **'무엇을 배웠는가'** 가 성공과 실패를 결정

### 상세 내용

**Build-Measure-Learn 순환 루프**

```
Build (MVP 제작) → Measure (사용자 반응 측정) → Learn (인사이트 도출) → Pivot or 지속 → 반복
```

**핵심 가설의 두 가지 축**

- **가치 가설 (Value Hypothesis)**: 사용자가 이 제품에서 가치를 느끼는가
- **성장 가설 (Growth Hypothesis)**: 사용자가 주변에 전파하는가

**MVP 유형 4가지**

| 유형                                 | 방식                                                 | 대표 사례           | 특징                                                  |
| ------------------------------------ | ---------------------------------------------------- | ------------------- | ----------------------------------------------------- |
| **영상 (Video) MVP**                 | 핵심 기능 시연 영상 공개                             | Dropbox             | 코드 없이 수요 증명. 하룻밤에 대기자 5천→75천 명      |
| **랜딩 페이지 (Landing Page) MVP**   | 소개 페이지만 제작, 클릭률·이메일 등록으로 수요 측정 | Buffer              | 제품 개발 전 유료 결제 의사 확인                      |
| **컨시어지 (Concierge) MVP**         | 사람이 직접 수동으로 서비스 제공                     | Airbnb              | 고객이 사람이 돕고 있음을 인지한 상태 (VIP 케어 느낌) |
| **오즈의 마법사 (Wizard of Oz) MVP** | 자동화처럼 보이지만 실제로는 사람이 수동 처리        | AI 서비스 초기 검증 | 고객은 자동화된 결과물이라고 믿는 상태                |

**MVP 유형 선택 기준**: '무엇을 만들지'가 아니라 **'어떤 가설을 가장 먼저 검증하고 싶은가'**

- 수요 확인 → 랜딩 페이지 MVP
- 경험 확인 → 컨시어지 또는 오즈의 마법사 MVP

**MVP 성공 사례의 3가지 공통점**

1. **핵심 가설의 단일화**: 단 하나의 핵심 가설 증명에 모든 자원 집중
2. **학습의 극대화**: 투입 비용은 최소화, 사용자 반응에서 얻는 학습량은 최대화
3. **실행과 검증의 속도**: 완벽한 제품보다 빠른 실행 우선

## 5. MoSCoW 기법 — 핵심 기능 우선순위 결정

### 핵심 개념

- 한정된 리소스 안에서 기능 중요도를 4단계로 분류하는 전략
- **Won't Have를 명시적으로 정의하는 것** 이 Scope Creep 방지의 핵심

### 상세 내용

| 분류            | 설명                                                 | 타이밍      |
| --------------- | ---------------------------------------------------- | ----------- |
| **Must Have**   | 없으면 출시 불가한 필수 기능. 제품의 핵심 가치 전달  | v1.0        |
| **Should Have** | 중요하지만 없어도 운영 가능. 바로 다음 업데이트 고려 | v1.1        |
| **Could Have**  | 있으면 만족도 상승, 없어도 무방. 여유 있을 때만 포함 | 이후        |
| **Won't Have**  | 이번 범위에서 명시적으로 제외. Scope Creep 방지 수단 | 다음 페이즈 |

---

## 6. PRD → MVP 설계 전체 흐름

```
Step 1. 문제 본질 파악
페르소나 + Pain Point → POV 문장 완성

Step 2. 제품 요구사항 정의
POV 기반 PRD 배경·목표 작성 → User Story 도출

Step 3. 우선순위 결정 및 MVP 범위 확정
MoSCoW 분류 → Must Have 도출 → MVP 범위 확정

Step 4. 프로토타이핑 및 AI 기반 구현
Figma 프로토타입 → AI 코딩 에이전트 구현 → 배포

Step 5. 시장 검증 및 성장 전략 수립
Business Model + ROI 분석 → 시장 검증 & 성장 전략
```

> 현재 과정은 **Step 3까지 완료**, Step 4~5는 프로젝트 기간에 진행 예정

## 오늘의 핵심 인사이트

- **PRD는 팀의 공통 언어다**: 같은 문서를 봐도 직군마다 다르게 상상하면 통합이 불가능해진다. PRD가 그 간극을 메운다.
- **MVP는 '작은 완성품'이 아니라 '가설 검증 도구'다**: Minimum에 집착하지 말고 Viable에 집중해야 한다. 고객이 실제로 쓸 수 없으면 MVP가 아니다.
- **Won't Have를 정의하는 것이 기획자의 진짜 역할**: 무엇을 만들지 결정하는 것보다 무엇을 만들지 않을지 결정하는 것이 더 어렵고 중요하다. Scope Creep을 막는 유일한 방법.
- **Dropbox, Airbnb, Buffer의 공통점**: 코드 한 줄 없이도, 에어매트리스만으로도 핵심 가설은 검증할 수 있다. 완벽한 제품보다 빠른 학습이 우선.
- **POV에서 PRD로 이어지는 흐름이 자연스럽게 연결된다**: 어제 만든 POV가 오늘 PRD의 배경이 된다. 문제 정의를 제대로 하면 제품 설계는 따라온다.
