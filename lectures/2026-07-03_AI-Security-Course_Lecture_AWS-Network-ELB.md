**OSI 7계층 — "어느 계층에서 무슨 일이 일어나는가"를 보는 틀**

TCP/UDP가 전송 계층(L4), HTTP/SSH가 응용 계층(L7)이라는 게 ALB(L7)와 NLB(L4)의 차이로 바로 연결됐다. ALB가 경로 기반 라우팅(`/api/auth` → A 인스턴스)을 할 수 있는 이유는 HTTP 헤더까지 들여다볼 수 있는 L7이기 때문이고, NLB는 IP/포트 수준인 L4라 빠르다. 어떤 도구가 어느 계층에서 작동하는지를 알면 "왜 이 도구가 이런 기능을 가지고 저런 기능은 없는지"가 보인다.

**데이터링크 계층의 MAC — 장치 식별자**

MAC 주소는 전자기기 MAC 주소 설정할 때 그 MAC이 맞다. 네트워크 인터페이스 카드(NIC)에 부여된 하드웨어 주소로, 같은 네트워크 안에서 장치끼리 통신할 때 쓰는 식별자다. IP가 논리적 주소(바뀔 수 있음)라면 MAC은 물리적 주소(하드웨어에 고정). L2(데이터링크)에서 같은 서브넷 안의 통신을 MAC으로 처리하고, L3(네트워크)에서 서브넷을 넘어갈 때 IP로 라우팅한다.

**TCP/UDP → WebSocket/LL-HLS 연결**

TCP/UDP를 배우면서 WebSocket과 LL-HLS가 어떻게 연결되는지 궁금해졌다. WebSocket은 TCP 위에서 HTTP 핸드셰이크 후 연결을 끊지 않고 유지하는 방식. LL-HLS는 HTTP/3(QUIC) 위에서 동작하는데, QUIC은 UDP 기반이라 TCP의 재전송 대기 병목 없이 낮은 지연을 달성한다. "UDP는 신뢰성이 낮다"는 게 단점이 아니라, 라이브 스트리밍처럼 속도가 중요한 상황에서는 오히려 TCP의 재전송 대기가 더 큰 문제가 된다는 맥락이 생겼다.

=**CloudWatch 알람 — 모니터링이 자동화와 연결되는 지점**

`stress-ng`로 CPU 부하를 줬을 때 EC2 t3.micro가 vCPU 2개라 `--cpu 1`로는 전체의 50%만 올라가 35%대에서 멈췄다. `--cpu 0`(전체 코어)으로 바꾸니 설정한 임계값(50%)을 넘겨 알람 메일이 발송됐다. 숫자만 보고 넘어갔으면 "왜 70% 설정인데 35%에서 멈추지?"가 의문으로 남았을 텐데, vCPU 개수와 `--cpu` 옵션의 관계를 직접 확인했다.

## 1. OSI 7계층

| 계층 | 이름 | 대표 프로토콜 |
|---|---|---|
| 7 | 응용 계층 | HTTP, SSH, DNS, FTP |
| 6 | 표현 계층 | ASCII, JPG |
| 5 | 세션 계층 | SSL, TLS |
| 4 | 전송 계층 | **TCP, UDP** |
| 3 | 네트워크 계층 | **IP**, ICMP, ARP |
| 2 | 데이터링크 계층 | Ethernet, MAC |
| 1 | 물리 계층 | ISDN, Wireless |

> **MAC 주소**: 데이터링크 계층(L2)에서 사용하는 하드웨어 식별자. 전자기기 설정에서 보이는 그 MAC 주소다. IP(논리적, 변경 가능)와 달리 NIC에 고정된 물리적 주소. 같은 서브넷 안의 통신은 MAC으로, 서브넷을 넘어가는 통신은 IP(L3)로 처리.

## 2. TCP vs UDP

| 구분 | TCP | UDP |
|---|---|---|
| 연결성 | 연결 지향 (3-way handshake) | 비연결 |
| 신뢰성 | 높음 (재전송, 순서 보장) | 낮음 |
| 제어 | 혼잡 제어, 흐름 제어 | 없음 |
| 속도 | 상대적으로 느림 | 빠름 |
| 주요 서비스 | HTTP, SSH, FTP | DNS, DHCP |

**계층과 로드밸런서의 관계**
- ALB(Application LB): L7 — HTTP 헤더/경로까지 읽을 수 있어서 경로 기반 라우팅 가능
- NLB(Network LB): L4 — IP/포트만 보므로 내용 불가, 대신 대규모 트래픽에 빠름

## 4. AWS VPC

- 퍼블릭 클라우드 내 논리적으로 격리된 가상 네트워크
- CIDR 블록으로 IP 대역 지정, 내부를 서브넷으로 분할

**주요 구성 요소**

| 구성 요소 | 역할 |
|---|---|
| 서브넷 | VPC 내부를 퍼블릭/프라이빗으로 분할 |
| 라우팅 테이블 | 서브넷 트래픽의 목적지 규칙 |
| 인터넷 게이트웨이 | 퍼블릭 서브넷 ↔ 인터넷 연결 |
| NAT 게이트웨이 | 프라이빗 서브넷 → 인터넷 단방향 (들어오는 요청 차단) |
| 보안 그룹 | 인스턴스 레벨 방화벽, 허용만 설정(기본 거부) |
| 네트워크 ACL | 서브넷 레벨 방화벽, 허용/거부 모두 설정 가능 |

## 5. EC2 모니터링 — CloudWatch

- 지표 기반 경보 설정 → 임계값 초과 시 알림(SNS, 이메일 등)
- CPU 사용률 50% 초과 시 알람 설정 후 `stress-ng`로 부하 테스트

```bash
# vCPU 1개만 사용 — t3.micro(vCPU 2개) 기준 최대 50%만 올라감
stress-ng --cpu 1 --cpu-load 70 --timeout 10m

# 전체 vCPU 사용 — 70% 이상 올라가 알람 트리거
stress-ng --cpu 0 --cpu-load 70 --timeout 10m
```

> `--cpu 1`은 코어 1개만 점유 → 전체 2코어 기준 최대 50% → 임계값 미달.
> `--cpu 0`은 전체 코어 점유 → 임계값 초과 → 알람 메일 발송.

## 6. 부하분산 서비스 (ELB)

- **고가용성**: 서비스가 지속적으로 작동 가능하도록 유지
- **내결함성**: 일부 구성 요소 장애에도 계속 작동

**Amazon ELB 구성 요소**

| 구성 요소 | 역할 |
|---|---|
| 로드 밸런서 | 트래픽 수신 및 분산 |
| 대상 그룹 | 분산 대상(EC2 등)의 집합 정의 |
| 리스너 | 포트/프로토콜 설정 |

**ALB vs NLB**

| 구분 | ALB | NLB |
|---|---|---|
| 계층 | L7 (응용) | L4 (전송) |
| 프로토콜 | HTTP/HTTPS | TCP/UDP/TLS |
| 경로 기반 라우팅 | ✅ (`/api/auth` → A, `/api/article` → B) | ❌ |
| 대규모 트래픽 | 상대적으로 낮음 | ✅ |
| 보안/필터링 | 간단한 기능 제공 | 없음 |
