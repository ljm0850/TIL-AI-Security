## 핵심 인사이트 모음

### 📅 2026-07-09

- 쿠버네티스는 완전히 처음이라 아직 전체 그림이 다 잡히진 않았지만, "왜 필요한가"부터 접근하니 감이 좀 왔다. 결국 Docker/Compose는 단일 호스트·소규모까지는 훌륭한데, 여러 서버(노드)에 걸친 대규모 운영에서 생기는 문제(수동 스케줄링, 로드밸런싱 부재, 확장 번거로움, 자가치유 부족 등)를 자동화된 추상화 레이어로 해결하는 게 K8s였다.
- 내 메모의 질문("k8s 쓰면 EC2에서 도커 여러 개 띄워 무중단 배포 로직을 직접 안 짜도 되나?")에 대한 답은 대체로 "그렇다"였다. K8s는 새 버전 팟이 정상(Healthy)임을 확인한 뒤 기존 팟을 점진적으로 교체하는 Rolling Update로 무중단 배포를 기본 제공하고, 컨테이너가 죽으면 재시작·재스케줄링하는 자가치유도 내장이라, 내가 배포 스크립트로 직접 짜야 했던 로직을 상당 부분 K8s가 대신 해준다.
- K8s의 핵심 철학이 "선언적(Declarative)"이라는 게 인상 깊었다. 명령형(Java/Python처럼 "어떻게" 할지 단계를 다 지정)과 달리, K8s는 "원하는 최종 상태(Desired State)"만 선언하면 현재 상태와 계속 대조하며 알아서 일치시킨다. 이 "현재 상태 vs 원하는 상태를 끊임없이 대조하는 루프"가 자가치유·스케일링의 근간이라는 게 연결됐다.  Compose의 선언적 방식이 클러스터 규모로 확장된 느낌.
- 클러스터가 컨트롤 플레인(두뇌)과 워커 노드(실제 앱 실행)로 이분되고, 모든 통신이 kube-apiserver라는 단일 중앙 허브를 통과한다는 구조가 핵심이었다. etcd조차 API 서버를 통해서만 접근 가능하게 막아둔 건 데이터 정합성 때문인데, 이 "단일 진입점" 구조는 통제·감사에는 유리하지만 동시에 API 서버가 노려지면 클러스터 전체가 위험해지는 지점이기도 하겠다는 생각이 들었다.
- CrashLoopBackOff의 엑스포넨셜 백오프는 개념 자체가 낯설지 않았다. Claude에 요청이 잘 안 갈 때 점점 간격을 늘려 재시도하는 것과 같은 결. 무한 재시작으로 자원을 태우지 않도록 재시도 간격을 기하급수적으로 늘리는 가드레일이라는 점에서 동일한 아이디어다.

## 1. Why Kubernetes? — Docker의 한계와 K8s의 해결책

### 핵심 개념
- Docker/Compose는 단일 컨테이너·소규모·로컬 개발엔 충분하지만, 상용 서비스의 고가용성·대규모 요구에는 한계. K8s가 이를 자동화 추상화로 해결

### 상세 내용 (6가지 도전 과제)
| 과제 | Docker의 한계 | K8s의 해결책 |
|---|---|---|
| 컨테이너 스케줄링 | 여러 노드에 수동 배치, 인적 오류 | 리소스 정의 기반 자동 분산 배치 |
| 로드 밸런싱 | 내장 LB 부재 | Service 개념으로 내장 LB 제공 |
| 애플리케이션 스케일링 | 수동 컨테이너 추가 + LB 수정 | HPA로 메트릭 기반 실시간 자동 확장/축소 |
| 자가 치유 | 재시작 정책이 exit code만 확인(먹통 감지 못 함) | 헬스 체크로 비정상 감지 → 재시작/재스케줄링 |
| 서비스 디스커버리 | 이름 통신은 되나 동적 대규모엔 부적합 | 내부 DNS + 고정 Service 엔드포인트 |
| 설정 관리 | 다중 환경 설정·키 수동 동기화 | ConfigMap/Secret으로 코드와 설정 디커플링 |

## 2. What is Kubernetes?

### 핵심 개념
- 컨테이너 오케스트레이션의 사실상 표준(De facto standard) 오픈소스 도구. Google이 개발해 2014년 오픈소스로 공개

### 상세 내용 (핵심 설계 원칙)
- **자동화 & 선언적 스타일**:
  - 명령형(How를 단계별 지정) vs 선언적(원하는 최종 상태만 선언, 도달 방법은 K8s가 판단)
  - K8s는 '현재 상태'와 '원하는 최종 상태'의 차이를 끊임없이 모니터링하고 일치시킴 → 이것이 자가치유·스케일링의 근간
- **확장성**: 트래픽 변화에 맞춘 수평 확장(인스턴스 개수 조절)을 쉽게 지원
- **회복 탄력성 & 가용성**:
  - 노드 장애 시 해당 노드의 팟을 건강한 다른 노드로 자동 재스케줄링
  - Rolling Update: 새 팟이 정상 구동을 확인한 후 기존 팟을 점진 교체 → 무중단 배포

## 3. 클러스터 아키텍처 — 컨트롤 플레인 vs 워커 노드

### 핵심 개념
- 'K8s 소프트웨어를 실행하는 영역(컨트롤 플레인)'과 '배포한 앱이 실행되는 영역(워커 노드)'을 명확히 구분

### 상세 내용
- **마스터 노드 (컨트롤 플레인 / 두뇌)**:
  - K8s 핵심 관리 프로세스가 실행되는 곳
  - 마스터가 다운되면 전체 클러스터 제어 불가(SPOF) → 프로덕션에선 2개 이상 다중 마스터로 HA 구성이 모범 사례
- **워커 노드 (Data Plane)**:
  - 실제 비즈니스 로직(앱/컨테이너/팟)이 구동되는 서버. 보통 워커 노드 수가 마스터보다 훨씬 많음

**영역별 컴포넌트** (※ 내 메모에서 컨트롤 플레인과 워커노드 컴포넌트가 섞였던 부분 정정)

- **컨트롤 플레인 (마스터 노드)**:
  - etcd (상태 저장 키-값 스토어)
  - kube-scheduler (팟 배치 결정)
  - kube-apiserver (중앙 엔드포인트)
  - kube-controller-manager (상태 유지 제어 루프)
  - cloud-controller-manager (클라우드 연동, **선택**)
- **워커 노드 — 필수(Mandatory)**:
  - kubelet (API 서버와 통신하며 팟 내 컨테이너 관리하는 에이전트)
  - Container Runtime (Docker/containerd 등 실제 컨테이너 구동 엔진)
  - kube-proxy (노드 네트워크 규칙 관리·트래픽 포워딩)
- **워커 노드 — 선택**: Services, Deployments, ReplicaSets, Ingresses, Jobs, StatefulSets 등 K8s 위에 생성하는 오브젝트

- **중앙 통신 메커니즘 (핵심)**: 모든 통신은 kube-apiserver를 통과하는 중앙 집중식. 사용자가 `kubectl`로 명령 → API 서버로 전달 → API 서버가 etcd/스케줄러/컨트롤러 매니저 및 워커 노드의 kubelet/kube-proxy와 상호 통신

## 4. The Control Plane — 컴포넌트 심층

### 핵심 개념
- 컨트롤 플레인은 클러스터가 사용자 의도대로 동작하도록 제어·관리하는 시스템 소프트웨어 집합(두뇌)

### 상세 내용
- **kube-apiserver**: Kubernetes API를 노출하는 유일한 중앙 진입점. 모든 조작·명령이 반드시 통과. `kubectl`이 사용자의 명령을 HTTP REST API로 번역해 전송
- **kube-scheduler**: 생성된 팟을 가용 자원을 고려해 가장 적합한 워커 노드에 배치 (예: 2GB RAM이 필요한 팟을, 1.5GB 남은 노드1 대신 4GB 남은 노드2에 배정). 리소스 외 제약조건·노드 선택 규칙도 종합
- **kube-controller-manager**: 지속적 감시 루프(Loop)로 '현재 상태'가 '원하는 상태'와 일치하는지 etcd 데이터 기반으로 계속 대조, 격차 발견 시 즉시 복구
  - Node Controller(노드 건강·등록 감시), Replica Set Controller(레플리카 개수 유지), Job Controller(일회성 태스크 관리)
  - 협업 예시: 팟 4개 선언했는데 3개만 도는 걸 ReplicaSet 컨트롤러가 발견 → API 서버에 생성 요청 → 스케줄러가 배치 노드 결정
- **etcd**: 모든 구성·상태 데이터가 저장되는 분산 키-값 스토어. 클러스터 상태의 유일한 진실의 원천(Single Source of Truth). 데이터 정합성을 위해 외부 컴포넌트의 직접 접근은 금지되고 오직 kube-apiserver를 통해서만 읽기/쓰기
- **cloud-controller-manager**: 하부 클라우드(AWS/GCP/Azure) API와 K8s를 연결하는 공급자 특정 컴포넌트. 클라우드 LB 연동, 영속성 스토리지(EBS/EFS 등) 매핑, 노드 수명주기 관리

> 💡 **노드와 VM의 관계**: K8s는 소프트웨어라 구동 인프라가 필요. 프로덕션은 '1 Node = 1 VM'으로 매핑해 HA 확보. 로컬은 `minikube`로 단일 장비 위에서 여러 노드를 시뮬레이션 가능 → 노드와 VM이 항상 1:1 물리적 동의어는 아님

## 5. kubectl CLI

### 핵심 개념
- K8s 클러스터와 상호작용하는 핵심 CLI. 명령을 API 서버가 이해할 HTTP REST API로 자동 번역해 전달

### 상세 내용
- **문법 구조**: `kubectl [Command] [Resource Type] [Resource Name] [Flags]`
- **3대 유스케이스**:
  - ① 조사·상태 확인(Inspect): `kubectl get`(목록·요약), `kubectl describe`(상세·이벤트 로그), `kubectl logs`(실시간 앱 로그)
  - ② 명령형 관리(Imperative): `kubectl run/scale/create/delete` — 파일 없이 즉시 생성·변경, 빠른 테스트·임시 조치에 유용
  - ③ 선언적 관리(Declarative): `kubectl apply/diff` — YAML 정의 파일 제출, 형상 관리 가능, 대규모 운영·CI/CD 표준

## 6. Pod — 개념과 생명주기

### 핵심 개념
- 팟은 K8s에서 생성·관리하는 가장 작은 배포 단위. 컨테이너는 단독 실행 불가, 반드시 팟에 캡슐화

### 상세 내용
**Pod 기본**
- 클러스터에서 실행 중인 프로세스의 단일 인스턴스. 컨테이너보다 높은 추상화(팟 단위로 환경변수/볼륨/보안/리소스 요청·제한 설정)
- 단일 컨테이너 팟(보편적): 서로 다른 메인 앱(웹+API)을 한 팟에 넣는 건 비권장, 각각 별도 팟으로
- 다중 컨테이너 팟(사이드카 패턴): 메인을 보조하는 프로세스 함께 실행 (Init Container, 로그·모니터링 수집 등)
- **자원 공유(핵심)**: 같은 팟 내 컨테이너는 네트워크 네임스페이스 공유 → `localhost:[포트]`로 직접 통신(단, 포트 중복 불가). 팟 레벨 볼륨을 함께 마운트해 동일 디렉터리 접근(컨테이너별 R/O·R/W 권한 선택 가능)
- 클러스터 내 모든 팟은 기본적으로 상호 통신 가능(네임스페이스가 달라도)

**Pod 생명주기 5단계**
- Pending: 컨테이너가 아직 실행 준비 안 됨 (스케줄링 대기 = 자원 부족 / 이미지 다운로드 중 = ContainerCreating)
- Running: 노드 할당·컨테이너 생성 완료, 최소 하나가 실행/시작/재시작 중이면 팟 전체는 Running
- Succeeded: 모든 컨테이너가 정상 완료(Exit 0) — 일회성 Job 등
- Failed: 모든 컨테이너 종료됐으나 최소 하나가 비정상(Exit≠0)
- Unknown: 마스터가 워커 노드(kubelet) 상태를 확인 못 해 팟 상태 수집 불가

> 💡 웹 서버(nginx/톰캣)는 항상 켜져 있어 보통 평생 Running. 앱 업데이트 시 K8s는 팟 내부 컨테이너만 바꾸는 게 아니라 **기존 팟을 통째로 삭제하고 새 이미지의 팟을 새로 만들어 배치**

**재시작 정책(Restart Policy)**
- Always(기본): 정상·에러 상관없이 무조건 재시작 (웹 서버 등)
- OnFailure: 에러(비정상 exit)일 때만 재시작
- Never: 재시작하지 않고 상태 그대로 방치

**CrashLoopBackOff & 엑스포넨셜 백오프**
- 컨테이너가 켜지자마자 죽는 무한 루프를 막는 가드레일
- 엑스포넨셜 백오프: 연달아 크래시할 때마다 재시작 간격을 기하급수적으로 늘림 (즉시 → 수초 → 1~2분 → 최대 5분)
- CrashLoopBackOff: 결함으로 계속 죽어서 K8s가 다음 재시작까지 대기 중인 상태
- 카운트 리셋: 수정 후 약 10~15분간 안정적으로 구동되면 백오프 카운트를 0으로 초기화 (이후 다시 죽으면 5분이 아니라 처음의 빠른 재시작부터 다시 시작)

**디버깅 필수 명령어**
- `kubectl describe pod [이름]`: 세부 명세·이벤트 로그(이미지 다운로드 실패, 볼륨 마운트 에러 등 힌트)
- `kubectl logs [이름]`: 컨테이너 내부 앱 로그(Fatal 에러, DB 연결 실패 등)
- `kubectl get pods -w`(--watch): 팟 상태 변화를 실시간 스트리밍 추적
