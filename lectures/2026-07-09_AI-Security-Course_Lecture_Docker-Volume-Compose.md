## 핵심 인사이트 모음

### 📅 2026-07-09

- 어제 Express 실습에서 "컨테이너 종료하면 인메모리 데이터가 사라진다"를 체감했는데, 오늘 그게 왜 그런지가 명확해졌다. 컨테이너 내부 데이터의 수명은 컨테이너 라이프사이클에 종속되고, stop/start로는 살아남지만 rm 하면 파일시스템 레이어까지 통째로 삭제된다. 그래서 DB처럼 상태를 가진(Stateful) 앱은 볼륨이 필수라는 결론. 상태 없는(Stateless) 웹 서버는 없어도 무방하다는 구분도 같이 잡혔다.
- 볼륨의 핵심은 "데이터와 애플리케이션 런타임의 디커플링". 데이터를 컨테이너에서 떼어내면 컨테이너는 언제든 갈아끼울 수 있는 일회용이 되고, 데이터는 그대로 남는다. 이게 어제 배운 "돌아가게 만드는 것 vs 운영 가능하게 만드는 것"의 연장선처럼 느껴졌다.
- `-v`와 `--mount`의 결정적 차이가 "호스트 경로가 없을 때"의 행동이라는 게 실무적으로 와닿았다. `-v`는 없는 경로를 root 권한으로 멋대로 만들어버려서 오타가 나도 조용히 엉뚱한 폴더가 생기는데, `--mount`는 에러를 내고 멈춘다. 즉 `--mount`가 실수를 조기에 잡아주는 안전한 방식이고, 그래서 공식 권장이라는 게 납득됨.
- 과거 팀에서 Docker Compose(`docker-compose.yml`)를 뭔지도 모르고 AI에 의존해 만들었던 게 있는데, 오늘 개념을 배우고 나니 그때 그 파일이 무엇이었는지 이제 읽힌다. `depends_on`은 컨테이너 시작 순서(예: api가 뜬 뒤 web) 보장이었고, `volumes`는 인증서 같은 걸 컨테이너에 물려주는 마운트였고, `services` 아래 각 블록이 컨테이너 하나씩이었다. 명령형으로 컨테이너를 일일이 run/link 하는 대신, 원하는 최종 상태를 선언해두면 Docker가 알아서 구성해준다는 "선언적 방식"의 실체를 뒤늦게 이해함.

## 1. 컨테이너 데이터의 한계와 볼륨의 필요성

### 핵심 개념
- 컨테이너 내부 데이터의 수명은 컨테이너 라이프사이클에 종속됨

### 상세 내용
- **stop & start**: 컨테이너를 중지했다 재시작해도 내부 데이터는 유지됨 (같은 컨테이너이므로)
- **stop & rm**: 컨테이너를 삭제하면 그 안의 파일시스템 레이어도 영구 삭제됨. 같은 이미지로 새 컨테이너를 만들어도 이전 데이터는 없음 (두 컨테이너는 "이미지 형제"일 뿐 서로 독립된 개체)
- **Stateless vs Stateful**:
  - Stateless(웹 서버 등): 데이터를 저장할 필요가 없어 기본 방식도 무방
  - Stateful(DB 등): 컨테이너 소멸·교체 후에도 데이터가 유지되어야 하거나 컨테이너 간 공유가 필요 → 데이터 유실이 치명적
- **결론**: 컨테이너 수명과 무관하게 데이터를 영구 보존하려면 볼륨(Volume)이 필수

## 2. Docker 볼륨 개요

### 핵심 개념
- 컨테이너 라이프사이클과 분리되어 데이터를 영구 보존하는 메커니즘. 컨테이너 파일시스템과 격리되어 Docker가 별도 관리

### 상세 내용
- 이점: 데이터 보존(삭제 후에도 유지), 데이터 공유(여러 컨테이너에 동시 마운트), 백업·복구 용이(앱과 분리), 디커플링을 통한 유연성(데이터와 런타임 분리)

**볼륨 유형 3가지**

| 유형 | 설명 | 사용 사례 |
|---|---|---|
| Bind Mounts | 호스트 시스템의 디렉터리/파일을 컨테이너에 직접 연결 | 실시간 개발 변경사항 반영에 이상적 |
| Named Volumes | 사용자가 생성, 여러 컨테이너 간 재사용 가능 | 데이터 영구 보존에 가장 적합 |
| Anonymous Volumes | 자동 생성되지만 식별 가능한 이름이 없음 | 영구 보존 불필요한 임시 데이터 (자주 안 씀) |

## 3. `-v` (--volume) vs `--mount`

### 핵심 개념
- 둘 다 볼륨을 컨테이너에 연동하는 옵션이지만 문법과 안전성에서 차이

### 상세 내용

| 비교 항목 | `--volume (-v)` | `--mount` |
|---|---|---|
| 문법 형태 | 콜론(`:`) 구분 단축형 | Key-Value 콤마(`,`) 형태, 명확함 |
| 존재하지 않는 호스트 경로 | 자동 생성함 | 에러를 내며 실행 실패 |
| Docker Swarm 지원 | 불가 | 가능(Swarm 필수) |
| 공식 권장 | 과거부터 쓰인 대중적 방식 | 현재 공식 권장 방식 |

- **결정적 차이 — 폴더 자동 생성 여부**:
  - `-v`: 호스트에 경로가 없으면 root 권한으로 강제로 폴더를 새로 만들고 실행 → 오타로 엉뚱한 빈 폴더가 생기는 문제 가능
  - `--mount`: 경로가 없으면 `invalid mount config` 에러를 내고 중단 → 오타나 세팅 미비를 조기에 잡아줘서 더 안전
- 예시:
```bash
# Named Volume 연동
docker run -e POSTGRES_PASSWORD=qwer1234 \
  --mount type=volume,source=myvolume01,target=/var/lib/postgresql \
  -d --name db-postgres postgres
```

## 4. Bind Mount

### 핵심 개념
- 호스트의 특정 디렉터리를 컨테이너 경로에 직접 연결 → 양쪽이 실시간으로 같은 파일을 봄

### 상세 내용
- 호스트에서 만든 파일이 컨테이너 안에서 보이고, 컨테이너 안에서 만든 파일이 호스트에도 즉시 생성됨 (PC 내 공유 폴더 같은 느낌)
- 예시:
```bash
docker run -e POSTGRES_PASSWORD=qwer1234 \
  --mount type=bind,source=/home/zynzza/dockers/mydata,target=/work \
  -d --name db-postgres postgres
# 단축형: -v /home/zynzza/dockers/mydata:/work
```
- 컨테이너 내부 `/work`에서 만든 디렉터리·파일이 호스트 `~/dockers/mydata`에 그대로 반영되는 것을 확인 가능 (→ 실습 파일 참고)

## 5. Docker Compose

### 핵심 개념
- Docker 환경에서 다중 컨테이너를 선언적으로 관리하는 도구

### 상세 내용
- **Plain Docker의 한계** (컨테이너가 8개쯤 되는 복잡한 아키텍처를 가정):
  - 수동 연결의 실수(엉뚱한 DB에 백엔드 연결 등)
  - 컨테이너 시작 순서(의존성) 보장 불가 (DB·캐시가 먼저 떠야 백엔드가 정상 동작)
  - 환경 간 일관성 유지 어려움 (로컬→스테이징 복제 시 환경 차이 버그)
  - 복잡한 네트워크·볼륨 수동 관리
  - 파편화된 환경변수 관리(충돌·오설정)
- **해결 — 선언적(Declarative) 방식**: `docker-compose.yml` 하나에 원하는 최종 상태(컨테이너/네트워크/볼륨/포트/의존성)를 정의하면 Docker가 알아서 빌드·구동
  - `depends_on`: 서비스 시작 순서 제어 (예: web은 db가 준비된 후 생성)
  - 네트워크·볼륨 자동화: 파일 내 정의만으로 독립 네트워크와 영구 스토리지 매핑
- **주요 활용 사례**:
  - 로컬 개발 환경 (가장 흔함) — 명령 하나로 전체 아키텍처를 일관되게 기동
  - 테스트·스테이징 — 프로덕션과 거의 동일한 환경 복제
  - CI/CD — `docker-compose up -d`로 띄우고 테스트 후 `down`으로 정리
  - 단일 호스트 단순 프로덕션 — 대규모는 K8s/Swarm이 낫지만, 단일 서버 단순 앱이면 충분한 선택지
