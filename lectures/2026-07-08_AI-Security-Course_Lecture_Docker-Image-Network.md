## 핵심 인사이트 모음

### 📅 2026-07-08

- 빌드 프로세스는 Docker CLI(터미널)가 실행하는 게 아니라, CLI는 "요청을 트리거"만 하고 실제 빌드는 Docker 서버(데몬)가 수행. 그래서 빌드할 때 현재 디렉터리(빌드 컨텍스트)가 통째로 데몬으로 업로드되는 거고, 여기에 5GB짜리 쓸데없는 파일이 있으면 그것까지 다 전송된다는 게 실습(fallocate로 5GB 파일 만들어 빌드)으로 와닿았다.
- 이미지 크기 최적화의 핵심이 내 코드 뿐만 아니라 베이스 이미지에도 있다는 게 인상적이었다. `docker history`로 뜯어보니 내가 통제하는 레이어는 11MB 남짓인데 베이스 이미지(node:22 → Debian Bookworm)에서 온 레이어가 1.1GB.  줄이려면 베이스 이미지를 alpine이나 distroless로 바꿔야 한다는 결론. "어디가 병목인가"를 먼저 봐야 한다
- 환경변수를 `.env.dev` / `.env.prod`로 분리하고 `--env-file`로 런타임에 주입하는 방식이 배포 자동화로 바로 연결된다는 걸 느꼈다. 로컬에서 `.env` 파일을 만들어 쓰던 경험이 있는데, 이걸 이미지에 굽지 않고(=`.dockerignore`로 배제) 실행 시점에 주입하면, 같은 이미지 하나로 dev/prod 환경을 갈아끼울 수 있음. `docker run --env-file .env.dev ...` 형태로 CI/CD에서 환경별 설정을 주입하는 그림이 그려짐.
- **컨테이너 간 통신**: 기본 브리지 네트워크는 컨테이너 이름 기반 통신(DNS 서비스 디스커버리)을 지원하지 않고, 사용자 정의 네트워크를 만들어야 이름으로 서로를 찾을 수 있다는 걸 실습으로 확인(기본 브리지에서 `curl web_server` 실패 → app-net에서 성공). 이건 같은 EC2 안에서 Spring 기반 서비스 A가 FastAPI 기반 AI 서비스 B를 호출하는 상황에 바로 대응되는 구조. 컨테이너는 재생성되면 IP가 바뀌니까 IP로 묶으면 취약하고, 이름으로 통신해야 유지보수가 된다. nginx 리버스 프록시도 이 위에서 동작하는데, 정확히는 nginx가 사용자 정의 네트워크의 서비스 디스커버리를 이용해 컨테이너 이름으로 백엔드를 찾아 요청을 넘기는 방식이다.
- `CMD`는 "기본값 제공"이라 런타임 인자가 오면 통째로 덮어써지고, `ENTRYPOINT`는 "고정된 실행 대상"이라 런타임 인자가 뒤에 붙는다(append). 이 둘을 조합하면 (ENTRYPOINT=고정 실행부 / CMD=기본 인자) CLI 도구처럼 "기본 동작은 있되 사용자가 인자로 바꿀 수 있는" 유연한 컨테이너를 만들 수 있다는 패턴이 깔끔했다.

## 1. 레이어 아키텍처 (Layered Architecture)

### 핵심 개념
- Dockerfile의 각 명령(instruction)이 최종 이미지 안에서 하나의 레이어를 생성
- 변경되지 않은 상위 레이어는 빌드 캐시로 재사용됨

### 상세 내용
- `docker history <image>`로 이미지의 레이어 구성을 확인 가능. 아래(먼저 생성)에서 위(최신)로 읽으면 Dockerfile에 추가한 명령들이 그대로 레이어로 반영된 것을 볼 수 있음
- 일부 레이어가 `<missing>`으로 표시되는 것은, 빌드 완료 후 최종 이미지에 통합되면서 독립적으로 존재할 필요가 없어진 중간 빌드 이미지를 Docker가 정리했기 때문
- **크기 최적화의 핵심은 베이스 이미지**: 내가 작성한 명령의 레이어는 약 11MB에 불과하고, 대부분의 크기(1.1GB)는 `FROM node:22`가 삼은 베이스(Debian Bookworm)에서 옴. 내 Dockerfile만 손봐서는 한계가 있고, 베이스 이미지를 바꿔야 획기적으로 줄어듦
- **빌드 캐시**: 상위 명령이 동일하고 뒷부분만 바뀌면, Docker는 변경되지 않은 상위 레이어를 재빌드하지 않고 캐시에서 가져와 빌드 시간을 크게 단축

## 2. 빌드 컨텍스트 (Build Context)

### 핵심 개념
- `docker build -t <name> .`에서 점(`.`)이 곧 빌드 컨텍스트: 현재 디렉터리 및 하위의 모든 파일

### 상세 내용
- 빌드는 CLI가 아니라 Docker 데몬이 수행함. CLI는 요청을 트리거할 뿐이고, 컨텍스트(디렉터리 전체)가 데몬으로 업로드됨
- 따라서 `node_modules`나 파이썬 venv 같은 무거운 디렉터리가 컨텍스트에 있으면 전부 업로드되어 빌드가 느려지고 이미지가 불필요하게 커짐
- 실습: `fallocate -l 5G some-large-file`로 5GB 파일을 만든 뒤 빌드하면, 로컬임에도 컨텍스트 업로드에 오랜 시간이 걸리는 것을 확인
- 베이스 이미지를 `node:22` → `node:22-alpine`으로 바꾸면 이미지 크기가 약 10배 작아지고 레이어 수도 훨씬 적어짐

## 3. .dockerignore

### 핵심 개념
- 빌드 컨텍스트에서 데몬으로 업로드하지 않을 파일을 지정하는 필터

### 상세 내용
- `COPY index.js index.js`처럼 대상을 하나하나 지정하는 방식은 실제 프로젝트에서 비실용적. Dockerfile은 `COPY . .`으로 단순하게 유지하고, 제외는 `.dockerignore`에 맡기는 게 정석
- 패턴 문법: `*`(단일 디렉터리 와일드카드), `**`(하위 디렉터리 포함), `?`(단일 문자), `!`(예외 처리)
- 예시:
```
some-large-file
**/*.test.js
```
- 테스트 파일(`*.test.js`)은 개발·CI에는 필요하지만 최종 이미지에는 포함할 필요가 없는 대표적인 제외 대상
- `.env*` 계열(`**/.env*`)도 반드시 제외 대상 — 민감정보가 담기고, 설정은 이미지에 굽지 않고 런타임에 주입하는 게 원칙 (→ 5번 참고)
- `COPY . .`으로 되어 있어도 데몬으로 컨텍스트를 보낼 때 `.dockerignore`에 걸린 파일은 필터링되므로 5GB 파일도 실제로는 제외됨

> 💡 이미지 내부 파일 확인: `docker run --rm -it <image> sh`로 접속하면 컨테이너 안의 파일 구조를 볼 수 있음. `--rm`은 종료 시 컨테이너 자동 삭제. 이때 Dockerfile의 기본 CMD를 `sh`로 일시 덮어쓴 것.

## 4. 환경 변수 (Environment Variables)

### 핵심 개념
- 컨테이너에 설정값을 전달하는 표준 방법. 3가지 층위(Dockerfile ENV / `-e` / `--env-file`)

### 상세 내용
- **Dockerfile `ENV`**: 이미지에 기본값을 굽는 방식. `ENV PORT=5000` → Node에서는 `process.env.PORT`로 접근. Dockerfile의 `ENV`명과 코드의 접근 키가 정확히 일치해야 함
- **`-e` / `--env`**: 이미지를 재빌드하지 않고 런타임에 값을 오버라이드. `docker run -e PORT=5001 ...`. 여러 개를 `-e A=.. -e B=..`로 동시 지정 가능
- **`--env-file`**: 변수가 많아지면 `-e`가 길어지므로 `.env` 파일로 분리. `docker run --env-file .env.prod ...`
  - `.env.dev`(PORT=3000), `.env.prod`(PORT=9000)처럼 환경별 파일을 두고 런타임에 갈아끼우면, 이미지를 다시 빌드할 필요 없이 같은 이미지로 dev/prod를 전환할 수 있음
  - `.env` 파일 안에서는 값에 따옴표를 붙이지 않아도 됨 (`-e`로 터미널에 직접 쓸 때는 공백 때문에 따옴표가 필요했던 것과 대비)
  - **보안**: `.env`는 API 키·DB 비밀번호 등을 담으므로 `.dockerignore`에 `**/.env*`로 반드시 배제. 설정 파일은 이미지에 굽지 않고 런타임에 주입하는 것이 올바른 방식

## 5. CMD vs ENTRYPOINT

### 핵심 개념
- `CMD` = 기본값(덮어써짐, Override), `ENTRYPOINT` = 고정 실행 대상(뒤에 추가됨, Append)

### 상세 내용
- **CMD**: 런타임에 인자를 주면 Dockerfile의 CMD가 완전히 무시되고 사용자 명령으로 대체됨
  - `docker run --rm cmd-example echo "..."` → CMD 내용 무시, 새 명령 실행
  - 완전히 다른 명령(`sh -c "..."`)을 던져도 동작 → 유연하지만 고정성이 없음
- **ENTRYPOINT**: 런타임 인자가 ENTRYPOINT 명령 뒤에 인자로 붙음
  - `ENTRYPOINT ["echo", "..."]` 이미지에 `docker run ... "hello"` → 기존 echo 뒤에 "hello"가 append되어 함께 출력
  - ENTRYPOINT 자체를 바꾸려면 반드시 `--entrypoint` 플래그 사용 (도커 플래그는 순서 민감 → 이미지 이름보다 앞에): `docker run --rm --entrypoint echo entrypoint-example "..."`
- **조합 패턴 (실무 권장)**: `ENTRYPOINT ["echo"]` + `CMD ["default message"]`
  - 인자 없이 실행 → `echo "default message"` (ENTRYPOINT + CMD 조합)
  - 인자 주면 → CMD만 덮어써지고 ENTRYPOINT는 유지 → `echo "custom message"`
  - 변하지 않는 실행부는 ENTRYPOINT, 사용자가 바꿀 옵션·인자는 CMD에 두는 패턴

| 인스트럭션 | 주 역할 | 런타임 동작 |
|---|---|---|
| CMD | 기본 명령/인자 | 사용자 인자 입력 시 전부 덮어써짐(Override) |
| ENTRYPOINT | 고정된 실행 대상 | 사용자 인자가 뒤에 추가됨(Append) |

## 6. Distroless 이미지

### 핵심 개념
- 앱 실행에 필수적인 런타임 의존성만 남기고 셸·패키지 매니저 등 OS 부가 기능을 전부 제거한 미니멀 이미지

### 상세 내용
- **장점**: 공격 표면(Attack Surface) 축소로 보안성 향상, 경량화(풀 속도·저장공간), 시작 속도 최적화, 감사 용이
- **도전 과제**: 셸·내장 도구가 없어 컨테이너 내부 디버깅이 어려움, 의존성을 빌드 단계에서 완벽히 포함시켜야 함, Dockerfile 복잡도·학습 곡선 증가
- **셸/패키지 매니저가 필요 없는 경우란?**: 멀티 스테이지 빌드로 이미 빌드가 끝난 실행물(컴파일된 바이너리, 설치 완료된 node_modules 등)만 넘겨받아 "실행만" 하는 경우. 런타임에 패키지를 새로 설치하거나 셸로 들어갈 일이 없으니 그것들을 뺄 수 있음
- 보안 관점: 셸·패키지 매니저가 없다는 건 공격자가 컨테이너를 뚫어도 내부에서 쓸 수 있는 도구가 없다는 뜻 → 침투 후 행동(lateral movement) 자체를 어렵게 만드는 심층 방어

## 7. 멀티 스테이지 빌드 (Multi-stage Build)

### 핵심 개념
- 하나의 Dockerfile에 여러 `FROM`을 두어 빌드 단계와 실행 단계를 분리하는 기법

### 상세 내용
- **문제**: 단일 `FROM`에서는 빌드에만 필요한 도구·의존성이 최종 이미지에 그대로 남아 용량이 커지고 보안에 취약
- **Distroless 단독 적용의 실패**: `FROM gcr.io/distroless/nodejs22`로 바꾸면 `RUN npm ci`가 실패함 — distroless에는 npm 같은 패키지 관리 유틸리티가 없기 때문
- **해결**: 빌드는 일반 node 이미지(도구 완비)에서 수행하고, 그 결과물(설치된 의존성 + 코드)만 distroless 이미지로 복사해 실행. "빌드용 대용량 이미지 → 실행용 최소 이미지"로 넘기는 구조
- 이렇게 하면 distroless의 보안·경량 이점을 취하면서도 외부 라이브러리 설치 문제를 우회할 수 있음

## 8. Docker 네트워크

### 핵심 개념
- 컨테이너의 격리를 유지하면서 컨테이너 간·외부 통신을 가능하게 하는 인프라

### 상세 내용
**네트워크 드라이버**

| 드라이버 | 설명 | 사용 사례 |
|---|---|---|
| Bridge (기본값) | 호스트 위에 컨테이너 간 통신용 프라이빗 네트워크 생성 | 대부분의 단일 호스트 시나리오 |
| Host | 컨테이너-호스트 네트워크 격리 제거 | 격리보다 최대 네트워크 성능이 필요할 때 |
| None | 모든 네트워킹 비활성화 | 특수한 격리 요구 |
| Overlay | 멀티 호스트 네트워킹 | Swarm 클러스터, 분산 애플리케이션 |

**기본 브리지 vs 사용자 정의 네트워크**
- Docker 설치 시 기본 네트워크 3개(bridge/host/none) 생성, `docker network ls`로 확인
- 기본 브리지: 컨테이너에 IP는 할당되지만 `DNSNames`가 null → **이름 기반 통신(DNS 서비스 디스커버리) 미지원**
  - 실습: ubuntu 컨테이너에서 `curl 172.17.0.2`(IP)는 성공, `curl web_server`(이름)는 `Could not resolve host` 실패
  - 컨테이너 재생성 시 IP가 바뀌므로 IP 기반 연결은 취약
- 사용자 정의 네트워크: `docker network create app-net`으로 생성 후 연결하면 `DNSNames`에 컨테이너 이름이 등록 → **이름 기반 통신 가능**
  - 연결 방법 2가지: 실행 중 컨테이너를 사후 연결(`docker network connect app-net web_server`) / 실행 시점에 연결(`--network app-net`)
  - 실습: app-net에 연결된 alpine에서 `curl web_server`(이름)로 nginx 응답 수신 성공
  - 하나의 컨테이너가 여러 네트워크에 동시 참여 가능(네트워크별 독립 IP 할당: bridge 172.17.0.2 / app-net 172.18.0.2)
  - 서브넷 `/16`(예: 172.18.0.0/16)은 약 65,000개 IP 할당 가능. `.0.1`은 게이트웨이 예약이라 첫 컨테이너는 `.0.2`부터

**호스트 네트워크와 포트 매핑**
- Host 네트워크: 격리를 제거하고 호스트 네트워크를 직접 사용. 컨테이너에 자체 IP가 할당되지 않음
  - Linux는 잘 지원되지만 macOS/Windows는 내부적으로 경량 VM을 거치기 때문에 원활히 지원되지 않음
  - **포트 충돌**: 같은 호스트 네트워크에서 nginx 두 개를 띄우면 두 번째는 `bind() to 0.0.0.0:80 failed (Address already in use)`로 즉시 종료. 격리가 없어 동일 포트 서비스를 여러 개 못 띄움 → 최후의 수단으로만 고려
- **권장 방식 (브리지 + 포트 매핑)**: 사용자 정의 브리지 네트워크를 만들고 필요한 포트만 바인딩
  - `docker network create app-net` → `docker run -d --name web_server --network app-net -p 80:80 nginx:1.30.0`
  - 호스트 80 → 컨테이너 80으로 포워딩. 격리를 유지하면서 필요한 채널만 안전하게 개방
  - 실무 기본값: `host` 네트워크 대신 **사용자 정의 브리지 + 포트 매핑(`-p 호스트:컨테이너`)** 조합
