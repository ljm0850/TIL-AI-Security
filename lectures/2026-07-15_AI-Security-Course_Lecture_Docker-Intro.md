## 핵심 인사이트 모음

### 📅 2026-07-15

- Docker의 본질은 **코드 + 실행 환경을 하나의 이미지로 묶어, 로컬·CI·클라우드 어디서든 같은 조건으로 실행되게 하는 것**. "내 로컬에선 되는데 서버에선 안 됨"의 근본 원인(파이썬 버전·패키지·env·포트가 환경마다 다름)을 없애는 게 목적이다.
- 이미지 = 읽기 전용 템플릿, 컨테이너 = 그걸로 실제 실행된 상태. 그래서 실패 진단이 두 갈래로 나뉜다 — 이미지 문제(코드/의존성)인지, 실행 옵션 문제(포트/env)인지. 이 구분이 디버깅의 첫 갈림길.
- **멀티스테이지 빌드**: builder에서 설치하고 runtime엔 결과물만 복사 → 빌드 도구·설치 캐시·임시 파일이 최종 이미지에 안 남는다. (보안 렌즈) 배포되는 아티팩트를 "실행에 필요한 것만"으로 최소화 = 이미지 크기와 공격 표면을 동시에 줄이는 것. 최소권한·격리 원리의 이미지판.
- **레이어 캐싱**: `pyproject.toml`을 먼저 COPY+설치하고 소스는 나중에 COPY. 코드만 바뀌면 의존성 설치 레이어를 캐시에서 재사용 → CI 반복 빌드 시간이 확 준다. 명령 순서가 곧 캐시 효율이라는 게 핵심.
- **.dockerignore**로 `.git`·`.env`·캐시를 제외 = 빌드 컨텍스트를 줄이는 동시에, (보안 렌즈) credential·불필요 파일이 이미지로 새어 들어가는 걸 막는 위생. 배포되는 아티팩트에 시크릿을 안 넣는다는 원칙.
- base image(`python:3.12-slim`)를 그대로 믿고 쌓는 구조 = **공급망 신뢰**.

### 📅 2026-07-16 (이어서)

- 이미지 태그는 결국 **"이 이미지가 어느 코드에서 나왔나"를 추적 가능하게 만드는 장치**. `latest`는 읽기 쉬운 대신 어느 커밋인지 추적이 안 되고, 커밋 해시 태그(github.sha)는 이미지↔코드를 1:1로 묶어준다. 팀 프로젝트를 떠올리면 main 자동배포에 PR 버전이나 커밋 해시 태그를 붙이는 게 맞겠다 싶다. (배포 사고 시 "어느 커밋이 떴나"를 바로 아는 게 곧 롤백/대응 속도)
- **빌드 성공 ≠ 서비스 가능**. 이미지가 빌드돼도 실행 명령·포트·초기화에서 막히면 요청을 못 받는다. 그래서 헬스체크(`/health`)로 "실행 중"이 아니라 "요청 처리 가능"을 따로 확인해야 한다. 이 `/health`가 뒤에서 ALB·ECS가 태스크 생사를 판단하는 기준으로 그대로 이어진다.
- **헬스체크가 여러 계층에 있다** — Docker `HEALTHCHECK`(컨테이너 자체 점검), ALB Target Group 헬스체크(트래픽 보낼지 판단), 앱 `/health`(실제 응답). 각각 다른 주체가 같은 질문("이거 살아있나")을 다른 위치에서 던지는 구조. (보안/운영 렌즈: 단일 지점이 아니라 계층별로 상태를 확인 → 한 계층이 속아도 다른 계층이 잡음)
- **Docker 빌드 자동화 = CI 성격의 빌드 검증**. ECR에 올리는 CD가 아니라, "코드 바뀔 때마다 이미지가 정상 생성되나"를 일관된 러너에서 확인하는 것. 로컬 빌드 성공은 내 PC 캐시/파일 상태에 의존할 수 있으니, 자동화 환경에서 한 번 더 거른다.

## 1. 이미지(Image)와 컨테이너(Container)

### 핵심 개념
- **이미지**: 컨테이너를 만들기 위한 읽기 전용 실행 템플릿. 코드·런타임·패키지·설정·실행 명령 포함.
- **컨테이너**: 이미지를 기반으로 실제 실행되는 환경.
- **레지스트리**: 이미지를 저장·배포하는 저장소. 공개=Docker Hub, AWS=ECR.

### 상세 내용
- **실행 환경을 코드로 관리하는 이점**: 앱은 소스 코드만으로 안 돈다(파이썬 버전·패키지·실행 명령·env·포트가 다 맞아야 함). 로컬에선 되던 게 서버에서 실패하는 건 대부분 이 조건들이 환경마다 달라서다. Dockerfile로 기록해 이미지로 만들면 로컬 확인·CI 빌드·AWS 배포에 동일 실행 기준을 적용.
- **이미지 vs 컨테이너 구분**: 이미지가 정상 빌드돼도 실행 명령·포트·env가 안 맞으면 컨테이너가 안 뜬다. 반대로 컨테이너 실행 실패 시엔 이미지 내부(코드/의존성) 문제인지 실행 시 옵션 문제인지 나눠 확인.
- **빌드(Build)**: Dockerfile 기준으로 이미지를 만드는 작업. 의존성 설치·코드 복사·기본 실행 명령 설정 포함.
- **실행(Run)**: 이미지를 컨테이너로 시작. 포트 연결·env·컨테이너 이름·실행 옵션을 함께 지정.
- **로그(Log)**: 컨테이너 내부 앱이 남기는 실행 기록. 컨테이너가 안 뜨거나 요청 처리 실패 시 원인 파악의 첫 단서.

## 2. Dockerfile 작성

### 핵심 개념
- 위→아래로 순차 처리. 명령 순서가 이미지 구성·캐시 재사용·빌드 속도·실행 안정성을 좌우.

### 상세 내용
- **베이스 이미지(FROM)**: 새 이미지의 출발점. `python:3.12-slim`은 가벼운 파이썬 기본 환경으로, 실행 PC의 파이썬 설치 상태와 무관하게 컨테이너 안에서 동일 버전을 쓰게 한다.
- **작업 디렉터리(WORKDIR)**: 이미지 내부 명령의 기준 경로. 지정하면 이후 COPY·RUN·CMD가 이 경로 기준으로 동작.
- **의존성(Dependency)**: FastAPI·Uvicorn처럼 실행에 필요한 패키지. `pyproject.toml`에 기록하면 코드와 실행 조건을 함께 버전 관리.
- **실행 명령(CMD)**: 컨테이너 시작 시 실행되는 기본 명령. 예: `uvicorn devmlops_docker.main:app --host 0.0.0.0 --port 8000` → 내부 FastAPI 앱을 외부 접속 가능한 웹 서버로 실행.

```dockerfile
FROM python:3.12-slim

WORKDIR /app
COPY pyproject.toml ./
COPY src ./src

RUN pip install --no-cache-dir .

EXPOSE 8000
CMD ["uvicorn", "devmlops_docker.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

## 3. 멀티스테이지 빌드

### 핵심 개념
- 하나의 Dockerfile 안에서 빌드 단계(builder)와 실행 단계(runtime)를 분리.

### 상세 내용
- **빌더 단계(builder)**: 가상환경 생성 + 패키지 설치. 설치에 필요한 도구·캐시가 쓰이지만, 최종 이미지엔 결과물만 전달.
- **런타임 단계(runtime)**: 실제 실행에 필요한 파일만 담는다. builder에서 만든 `/opt/venv`와 앱 코드만 복사 → 임시 파일·설치 캐시·빌드 도구가 최종 이미지에 안 남음.
- **가상환경(/opt/venv)**: 시스템 파이썬과 앱 의존성이 섞이는 걸 줄여, 컨테이너 안에서 어떤 패키지를 기준으로 실행되는지 예측하기 쉽게 한다.

```dockerfile
# 빌드 단계: 패키지 설치
FROM python:3.12-slim AS builder
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY pyproject.toml ./
RUN pip install --no-cache-dir .

# 실행 단계: 실행에 필요한 파일만 복사
FROM python:3.12-slim AS runtime
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
COPY src ./src
ENV PATH="/opt/venv/bin:$PATH"
EXPOSE 8000
CMD ["uvicorn", "devmlops_docker.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

## 4. 레이어 캐싱

### 핵심 개념
- 각 단계 실행 결과를 저장해두고, 변경되지 않은 단계는 이전 빌드 결과를 재사용.

### 상세 내용
- **레이어(Layer)**: 이미지가 만들어지는 과정에서 생기는 변경 단위. FROM은 베이스 이미지 레이어를 가져오는 출발점, RUN·COPY·ADD는 새 변경 레이어를 만든다.
- **캐시(Cache)**: Dockerfile 명령과 해당 단계 입력 파일이 안 바뀌면, 그 단계는 재실행 없이 기존 레이어를 재사용.
- **순서 전략**: `pyproject.toml`을 먼저 COPY+설치하고 소스 코드를 나중에 COPY하면, 코드만 바뀐 경우 의존성 설치 단계를 캐시에서 재사용. (CI에서 매번 의존성부터 다시 깔면 빌드 시간이 불필요하게 늘어남)
- **.dockerignore**: 빌드에서 제외할 파일 목록. `.git`·`.venv`·캐시·빌드 결과물을 제외하면 빌드 컨텍스트가 작아지고, 불필요 파일이 이미지에 포함되는 걸 줄인다.

## 5. 이미지 태깅 전략

### 핵심 개념
- 이미지 태그(Tag) = 이미지 이름 뒤에 붙는 식별자. 레지스트리에 이미지가 쌓일수록 "어느 코드에서 만든 이미지인가"를 구분할 방법이 필요.

### 상세 내용
- **latest 태그**: 관례적으로 가장 최근 이미지를 가리키는 용도. 간단·읽기 쉬움. 단, 어떤 코드로 만들어졌는지 추적이 어렵다.
- **커밋 해시 태그(Commit Hash Tag)**: Git 커밋 값을 태그에 반영. 코드 변경과 이미지 산출물을 연결 → CI/CD에서 특정 배포 결과가 어느 커밋에서 나왔는지 확인할 때 유용. (실습에선 `github.sha` 앞 7자리 사용)
- **버전 태그(Version Tag)**: `v1.0.0`처럼 사람이 정한 릴리스 기준. 운영 배포·릴리스 관리엔 적합하지만 매 커밋마다 쓰기엔 버전 관리 부담.
- 실무 감각: latest만 쓰면 운영 이미지의 코드 상태 추적이 어려워짐 → 커밋 해시 태그로 이미지↔코드 연결을 남기는 게 배포 검증·롤백 시점에 도움.

## 6. 컨테이너 실행과 헬스체크

### 핵심 개념
- 빌드 성공과 서비스 가능 상태는 별개. 컨테이너를 실행하고, 실제로 요청을 처리할 수 있는 상태인지 따로 판단.

### 상세 내용
- **포트(Port)**: 컨테이너 내부 서비스가 요청을 받는 통로. Dockerfile `EXPOSE 8000`은 "8000 포트를 쓴다"는 정보를 이미지에 기록할 뿐, 외부 공개 설정이 아님 → 외부 접근하려면 실행 시 포트 바인딩 필요.
- **호스트 바인딩(Host Binding)**: 컨테이너 내부 포트를 로컬 PC 포트와 연결하는 설정. `-p 8000:8000`으로 지정하면 브라우저나 curl로 `http://localhost:8000/health` 접근 가능.
- **헬스체크(Health Check)**: 컨테이너가 "실행 중"인지가 아니라 "실제로 요청 처리 가능한 상태"인지 확인. 보통 `/health` 엔드포인트가 `status: ok`와 버전 값을 반환하도록 구성. 이 흐름이 뒤에서 ALB·ECS가 서비스 상태를 판단하는 방식으로 이어짐.

```bash
# 이미지 빌드
docker build -t devmlops-fastapi:local .

# 컨테이너 실행 (로컬 8000 포트와 연결)
docker run -d -p 8000:8000 --name devmlops devmlops-fastapi:local

# 컨테이너 로그 확인
docker logs devmlops

# 헬스체크 확인
curl http://localhost:8000/health
# 정상 응답 예시: {"status": "ok", "version": "0.1.0"}
```

## 7. Docker 빌드 자동화 (GitHub Actions)

### 핵심 개념
- GitHub Actions에 Docker 빌드 단계를 추가하는 이유: 로컬에서 성공한 빌드를 일관된 자동화 환경에서 재확인. (이번 실습의 자동화는 ECR에 올리는 CD가 아니라, 이미지 정상 생성 여부를 확인하는 CI 성격의 빌드 검증)

### 상세 내용
- **워크플로우**: `.github/workflows/`의 YAML. 여기선 Docker 이미지 빌드 검증 담당.
- **러너**: `ubuntu-latest`에서 Docker 빌드 실행.
- **빌드 캐시(Build Cache)**: 이전 빌드 결과 재사용으로 빌드 시간 절감. `cache-from`, `cache-to` 옵션으로 반복 빌드에서 안 바뀐 레이어 재사용.
- 이미지 태그에 `github.sha`를 쓰면 배포된 이미지가 어느 커밋에서 나왔는지 추적 쉬움.

```yaml
name: Docker Build

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Docker 이미지 빌드
        run: |
          docker build \
            -t devmlops-fastapi:${{ github.sha }} \
            -t devmlops-fastapi:latest \
            .
      - name: 이미지 생성 확인
        run: docker image inspect devmlops-fastapi:${{ github.sha }}
```
