## 핵심 인사이트 모음

### 📅 2026-07-01

**프로세스 시그널 — 커널이 Ring 3에 직접 개입하는 인터페이스**

`kill`이 "무시 불가능"하다는 게 처음엔 그냥 명령어 특성으로 읽혔는데, 6/29에 정리했던 Ring 0/3 구조와 연결하면 다르게 보인다. `SIGKILL`은 커널(Ring 0)이 프로세스(Ring 3)에 직접 보내는 신호라 프로세스가 가로채거나 무시할 수 없다. Ring 3은 Ring 0의 명령을 거부할 권한이 없다. 반면 `SIGTERM`이나 `SIGSTOP` 같은 시그널은 프로세스가 핸들러를 등록해서 처리 방식을 바꿀 수 있다.

AI 에이전트가 자식 프로세스를 spawn하는 시나리오로 옮겨보면: 에이전트가 실행한 프로세스를 누가 어떤 권한으로 종료할 수 있는지가 보안 경계가 된다. 에이전트 프로세스가 예상치 못한 동작을 하거나 멈추지 않을 때, 그 프로세스를 강제 종료할 수 있는 건 커널 수준의 개입(`SIGKILL`)뿐이고 — 이게 결국 권한 모델의 문제다.

**환경변수 → 자식 프로세스 전달 = 민감값 노출 경로**

셸 변수는 현재 셸 세션에만 존재하지만, `export`로 환경변수가 되면 그 프로세스가 spawn하는 모든 자식 프로세스에 자동으로 전달된다. 이게 편리함의 이면에 위험이 있다 — 환경변수에 API 키나 DB 비밀번호 같은 민감값이 들어 있으면, 그 프로세스에서 실행되는 모든 자식 프로세스(LangChain이 `@tool`로 호출하는 셸 명령 포함)에 그 값이 그대로 흘러들어간다. 부모 프로세스가 가진 환경변수를 자식이 읽을 수 있다는 건, 에이전트가 실행하는 외부 명령이 환경에서 민감값을 탈취하는 공격 경로가 될 수 있다는 뜻이다.

로그인 셸 시작 시 `.profile` → `.bashrc` 순서로 환경이 로드되는 구조도 이 맥락에서 이해된다 — 어떤 변수가 어느 범위(로그인 셸 전체 vs 비로그인 셸 세션)에서 살아있는지가 환경변수 관리의 핵심이다.

**SSH — 평문 전송의 대안이 왜 필수인가**

`rlogin`, `telnet`은 로그인 이름과 비밀번호를 포함한 모든 통신을 평문으로 전송했다. 네트워크에서 패킷을 가로채면 그대로 읽힌다. SSH는 이 문제를 해결하기 위해 설계된 암호화 프로토콜이다. AWS 서버에 SSH 키 기반 인증만 허용하고 비밀번호 인증을 끄는 게 표준인 이유가 여기서 정리된다 — 어제 정리한 `PasswordAuthentication no`가 왜 기본값인지 그 역사적 맥락.

**AI 에이전트 산출물 재접근 차단 — 소유권 분리가 핵심**

환경변수 키 노출 문제를 생각하다가 "쓰기만 주고 읽기를 없애면 에이전트가 자기 산출물을 다시 못 읽지 않을까"라는 아이디어가 나왔다. 검증해보니 chmod로는 안 되고 소유권 분리가 핵심이었다. 단독 통제는 아니고 심층 방어 한 겹이지만, 이런 방향으로 생각이 뻗어나간다는 게 과거의 나와 달라진 지점이다. 상세 분석은 본문 7번 참조.

**`find` 필터 순서가 성능에 영향을 준다**

```bash
$ find ~ -type f -name '*.txt' -print   # type 먼저
$ find ~ -name '*.txt' -type f -print   # name 먼저
```

두 명령의 결과는 같지만 연산 횟수가 다를 수 있다. `find`는 표현식을 왼쪽부터 순서대로 평가하고, 앞 조건이 실패하면 뒤 조건은 평가하지 않는다(단락 평가, short-circuit evaluation). 그러므로 더 많은 파일을 일찍 걸러내는 조건을 앞에 두는 게 유리하다. 탐색 대상 파일이 많아질수록 — 대규모 서버 로그 디렉토리에서 find를 돌리는 경우 등 — 이런 최적화가 의미를 가진다. 당장 외울 필요는 없지만, "조건의 순서가 성능에 영향을 준다"는 원칙은 SQL WHERE 절 최적화와도 같은 패턴이다.

**셔뱅(shebang) — OS에게 인터프리터를 명시하는 계약**

`#!/usr/bin/python3`이나 `#!/usr/bin/bash` 첫 줄이 단순한 주석처럼 보이지만, 커널이 이 파일을 실행할 때 어떤 인터프리터로 해석할지를 명시하는 역할을 한다. 이게 없으면 OS는 파일을 어떻게 실행해야 할지 모른다. 스크립트를 실행 가능하게 만들고(`chmod +x`), 셸이 찾을 수 있는 PATH에 배치하는 흐름이 자동화의 기본 단위.

### 📅 2026-07-02

**히어 도큐먼트(heredoc) 안에서도 명령 치환이 먼저 실행된다**

`cat << _EOF_` 블록 안의 `$(report_uptime)` 같은 명령 치환은 heredoc 내용이 출력되기 *전에* 셸이 먼저 평가한다. 함수가 정의되지 않았으면 이 시점에 에러가 stderr로 찍히고, 그 후 나머지 HTML이 stdout으로 출력된다. 에러가 먼저 보이는 게 이상해 보이지만, stderr와 stdout은 독립된 스트림이라 순서가 뒤섞여 보이는 것. `$()`는 현재 셸이 서브셸(자식 프로세스)을 띄워 실행하는데, 그 서브셸의 stderr가 부모 셸의 터미널을 공유하기 때문에 그대로 찍힌다.

**셸 변수 스코프 — Python의 전역변수와 다른 계층 구조**

셸 스크립트 안의 변수는 Python 전역변수처럼 그 프로세스 안에서만 전역이다. "OS 위의 모든 프로그램"에 퍼지는 게 아니냐는 의문이 들었는데, 정리하면:

| 스코프 | 방법 | 범위 |
|---|---|---|
| 셸 변수 | 일반 선언 | 현재 셸 프로세스 안에서만 |
| 환경변수 | `export` | 현재 프로세스 + 자식 프로세스 (아래 방향만) |
| 시스템 전체 | `/etc/environment`, `/etc/profile` | 새로 시작되는 세션부터 적용 |

`export`해도 부모·형제 프로세스에는 올라가지 않는다. 프로세스 트리 아래 방향으로만 흐른다. Python의 로컬/전역/모듈 스코프처럼 셸도 스코프가 계층적으로 존재한다는 구조적 이해가 핵심.

**배열 접근 — `$days[2]` vs `${days[2]}`**

```bash
days=([0]=SUN [1]=MON [2]=TUE [3]=WED)
echo $days[2]    # SUN[2] — $days가 먼저 확장되어 SUN이 되고, [2]는 문자열로 붙음
echo ${days[2]}  # TUE   — 중괄호로 감싸야 배열 인덱스 접근
```

`$days[2]`가 C의 포인터처럼 느껴졌는데, 정확히는 셸의 확장 우선순위 문제다. 중괄호 없이는 `$days`(인덱스 0)가 먼저 확장되고 `[2]`는 그냥 문자열로 붙어버린다. 배열을 다룰 때 `${}`가 필수인 이유.

## 1. 프로세스

### 핵심 개념
- 모든 실행 중인 프로그램은 프로세스. OS는 각 프로세스에 PID(Process ID)를 부여
- 포그라운드 vs 백그라운드: 터미널을 점유하느냐의 차이

### 상세 내용

**프로세스 제어**

| 동작 | 방법 | 결과 |
|---|---|---|
| 백그라운드 실행 | `command &` | 터미널 점유 없이 실행 |
| 포그라운드 중단 | `Ctrl+C` | 프로세스 종료(SIGINT 전송) |
| 포그라운드 일시정지 | `Ctrl+Z` | Stopped 상태로 백그라운드 전환 |

**시그널 종류**

| 시그널 | 의미 | 프로세스가 무시 가능? |
|---|---|---|
| `SIGKILL` (9) | 커널이 즉시 강제 종료 | ❌ 불가능 |
| `SIGTERM` (15) | 정상 종료 요청 | ✅ 핸들러로 처리 가능 |
| `SIGSTOP` | 일시 정지 | ❌ 불가능 |

> `SIGKILL`은 Ring 0(커널)이 Ring 3(프로세스)에 직접 개입하는 것이라 프로세스 레벨에서 거부 불가. `kill -9 PID`가 "확실한 종료"로 통하는 이유.

## 2. 환경변수와 셸 시작 파일

### 핵심 개념
- **셸 변수**: 현재 셸 세션에만 존재
- **환경변수**: `export`로 선언, 자식 프로세스에 자동 전달

### 상세 내용

**로그인 셸 시작 순서**

```
로그인 셸 실행
  → .profile 로드
    → Bash라면 .bashrc 로드 (비로그인 셸 세션용 설정 포함)
```

```bash
# ~/.profile 일부
if [ -n "$BASH_VERSION" ]; then
    if [ -f "$HOME/.bashrc" ]; then
        . "$HOME/.bashrc"   # source와 동일
    fi
fi
```

- `source` == `.` : 스크립트 파일을 현재 셸에서 읽어 실행 (새 자식 프로세스를 만들지 않음)
- `.profile`에서 `/usr/bin` 등이 PATH에 등록되므로, PATH 변경 후에는 `.profile`을 다시 읽거나(`source ~/.profile`) 세션을 재시작해야 반영됨

## 3. 네트워킹

### IP 주소

- **공인 IP**: 인터넷에서 유일한 식별자. 공유기(라우터)에 할당
- **사설 IP**: 내부 네트워크(가정, 회사)에서만 유효한 주소. 공유기가 내부 기기에 분배

**서브넷 마스크**
- `203.0.113.42/24`: 앞 24비트가 네트워크 주소, 나머지 8비트가 호스트 주소
- IP 주소와 서브넷 마스크를 비트 AND 연산 → 네트워크 주소 도출
- `ip a` 명령으로 현재 인터페이스의 IP 확인

### SSH

- `telnet`, `rlogin`: 모든 통신(비밀번호 포함)을 **평문** 전송 → 패킷 스니핑으로 탈취 가능
- **SSH**: 암호화된 채널로 원격 로그인. 키 기반 인증을 함께 쓰면 비밀번호 탈취 자체를 차단
- AWS 서버 표준: `PasswordAuthentication no` + SSH 키 페어만 허용

## 4. 파일 검색 — `find`

### 핵심 개념
- `find`는 조건 표현식을 **왼쪽부터 순서대로 평가** (단락 평가)
- 더 많은 파일을 일찍 걸러내는 조건을 앞에 두는 게 성능상 유리

### 상세 내용

**기본 사용**
```bash
find ~ -type f -name "*.txt"           # 일반 파일 중 .txt
find ./ -type f -name 'file-B' -exec touch '{}' \;  # 찾은 파일에 명령 실행
# \; : -exec의 끝을 나타내는 구분자
```

**크기 단위 주의 (`-size`)**

`find`의 크기 단위는 512B 블록 기준으로 올림 처리한다.

| 표현 | 의미 |
|---|---|
| `-size 1M` | 블록 올림 기준 1M인 것 (1byte~1M 사이 파일 모두 해당) |
| `-size +1M` | 1M 초과 |
| `-size -1M` | 1M 미만 = 0블록 = 사실상 빈 파일만 |

**필터 순서와 성능**
```bash
find ~ -type f -name '*.txt' -print   # type 먼저 — 원칙적으로 더 유리할 수 있음
find ~ -name '*.txt' -type f -print   # name 먼저 — 결과는 동일
```
대규모 파일 시스템에서는 조건 순서가 실질적인 성능 차이를 만든다. SQL WHERE 절 최적화와 같은 원칙.

### 핵심 개념

## 6. 셸 스크립트

### 핵심 개념
- 명령어가 담긴 텍스트 파일. 셸이 읽어서 순서대로 실행 → 자동화의 기본 단위
- 작성 → 실행 권한 부여(`chmod +x`) → PATH에 배치 순서

### 셔뱅(shebang) `#!`
```bash
#!/usr/bin/bash
echo 'Hello Linux World!!!'
```
```python
#!/usr/bin/python3
print("Hello Python World")
```
- 파일 첫 줄에 인터프리터 경로를 명시. 커널이 이 파일을 실행할 때 어떤 프로그램으로 해석할지를 OS에게 알려주는 역할
- 없으면 현재 셸이 해석을 시도하거나 실행 방법을 모름

### PATH 등록
- `.profile`에서 `/usr/bin` 등이 PATH에 추가됨
- 커스텀 스크립트를 PATH에 있는 디렉토리에 배치하거나, `.profile`에 직접 경로 추가 후 `source ~/.profile`로 반영

## 7. AI 에이전트 산출물 — 소유권 분리를 통한 재접근 차단

### 아이디어 발생 맥락
환경변수를 통한 키 노출 문제를 생각하다가 나온 질문: 쓰기 권한만 주고 읽기를 없애버리면 AI가 만든 결과물을 에이전트 자신이 다시 읽지 못하게 막을 수 있지 않을까? Claude와 대화하며 이 아이디어를 검증했고, 아래가 그 결론이다.

### 핵심 — 권한이 아니라 소유권이 문제
단순히 `chmod 200`(쓰기만, 읽기 제거)으로는 부족하다. 파일을 생성한 주체가 소유자가 되고, 소유자는 자기 파일의 권한을 언제든 되돌릴 수 있다(`chmod 600`으로 읽기 복구 가능). 막아야 할 건 권한 비트가 아니라 **소유권 자체**.

### 이 방어가 실제로 막는 것 — 딱 하나
에이전트가 자기 산출물을 **나중에 다시 읽는 경로**. 유출 전반이 아니다. 비밀값은 이미 에이전트 손에 있으므로, 네트워크(egress)나 환경변수 직접 접근이 열려 있으면 이 방어만으로는 유출을 막을 수 없다. 단독 통제가 아니라 **심층 방어(defense-in-depth)의 한 겹**으로 위치시켜야 정확하다.

뿌리 통제는 따로 있다: (a) 애초에 비밀을 노출 안 하기(secret broker/단기 토큰), (b) egress 필터링, (c) taint 추적. 이것들이 실패했을 때의 보조 레이어.

유효한 조건: 휘발성 컨텍스트 + 비밀이 산출물에 우발적으로 섞이는 경우(로그·env 덤프 등). 이 조건에서만 "다음 세션의 재수집 차단"이 실질 가치를 가진다.

### 구현 — "매개된 쓰기(mediated write)"만 성립

| 방식 | 성립 여부 | 이유 |
|---|---|---|
| 별도 저장 서비스가 대신 생성 / FUSE 데몬 / 객체 스토리지 PUT-only | ✅ | 에이전트가 어느 순간에도 소유자가 아님 |
| ACL | ❌ | 새 파일 소유자는 여전히 생성 프로세스(에이전트) |
| 사후 `chown` | ❌ | chown 이전까지 TOCTOU 읽기 창 존재 + root 권한 필요 |

### 전제 조건 (깨지면 무력화)
- 에이전트와 master가 다른 UID + 권한 상승 경로 없음(sudo/ptrace/바이너리 변조 불가)
- master가 그 산출물을 다시 에이전트/LLM 컨텍스트로 되먹이지 않음 (파일 권한은 데이터 흐름을 추적하지 못함)

### 적용 가능한 곳
- **AI 에이전트 샌드박싱**: 코드 실행/툴 사용 에이전트의 출력물 격리 (Claude Code류 작업 디렉토리 권한 설계)
- **CI/CD 시크릿 격리**: 빌드 스텝이 만든 로그·아티팩트에 시크릿이 섞여도 후속 스텝이 재수집 못 하게
- **멀티테넌트 write-only 드롭박스**: 업로더가 자기가 올린 것도 못 읽는 제출함 패턴

### 참고 — 디렉토리 권한 r/w/x의 의미
파일과 달리 디렉토리에서 의미가 다르다.

| 권한 | 디렉토리에서의 의미 |
|---|---|
| r | 목록 조회 (`ls`) |
| w | 파일 생성/삭제 |
| x | 디렉토리 진입 (`cd`) |

`x`만 주고 `r`을 제거하면 진입은 되지만 `ls`로 목록을 볼 수 없다. 파일 이름을 정확히 알아야만 접근 가능한 상태 — 보안 목적으로 의도적으로 쓰이는 패턴.
