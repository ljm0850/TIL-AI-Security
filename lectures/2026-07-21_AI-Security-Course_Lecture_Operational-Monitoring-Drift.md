## 핵심 인사이트 모음

### 📅 2026-07-21

- **배포 검증과 운영 모니터링은 확인하는 시점도, 대상도 다르다.** 배포 검증은 "그 순간에 잘 올라갔는가"를 본다. 운영 모니터링은 "지금도 요청을 제대로 처리하고 있는가"를 계속 본다. 그동안 배포 성공 로그를 보면 그 뒤는 생각 안했는데, 배포가 끝난 뒤에 트래픽이 늘거나 컨테이너가 재시작되거나 입력 데이터 성격이 바뀌는 일은 배포 기록 어디에도 남지 않는다.
- **드리프트는 "실패로 나타나지 않는 실패"** 지금까지 배운 문제들은 어떤 형태로든 신호를 냈다 — 헬스체크 타임아웃, assert 실패, traceback. 드리프트는 다르다. **CloudWatch 같은 서비스의 오류 로그로는 확인할 수 없다.** API는 200을 잘 돌려주고, 로그도 깨끗하고, 태스크도 정상인데 예측만 틀린다. 실패 신호가 없는 실패를 잡으려면 아예 다른 관측 수단이 필요
- **데이터 드리프트와 개념 드리프트의 구분이 원인 추적 방향을 정한다.** 입력 분포가 학습 시점과 달라지는 게 데이터 드리프트고, 입력은 그대로인데 입력과 정답의 관계가 달라지는 게 개념 드리프트다. 전자는 들어오는 데이터를 보면 감지할 수 있지만, **후자는 정답을 알아야만 감지할 수 있다.** 그러면 개념 드리프트는 사실상 뒤늦게만 발견된다는 뜻
- **"로깅 원칙"의 답이 이틀에 걸쳐 나왔다.** 어제는 "Secrets를 가공해 출력하면 마스킹이 풀린다"였고, 오늘은 "관찰에 필요한 입력값도 그대로 남기면 안 된다"였다. 로깅 원칙은 **"무엇을 남길지"가 아니라 "무엇을 남기면 안 되는지를 먼저 정한 다음, 그 제약 안에서 최대한 관찰 가능하게 만드는 것"**에 가깝다.
- **메모한 질문에 대한 오늘의 답.** "파라미터·데이터를 자동화로 대량 생성·평가할 때 MLOps의 진가가 나오는가?"라고 적었는데, 절반만 맞았다. Airflow 부분이 그 방향의 확장이 맞긴 하다. 그런데 오늘 실습에서 본 건 **재학습을 딱 한 번만 해도** champion이 흔들리고 배포 대상이 바뀐다는 것이었다. 진가는 실행 횟수가 많을 때뿐 아니라 **나중에 "그때 그 모델이 왜 그랬는지" 되짚어야 할 때** 나온다.

## 1. 운영 모니터링이 필요한 이유

### 핵심 개념

**운영 모니터링(Operational Monitoring)**: 배포 후 서비스 상태, 성능, 모델 품질을 지속해서 확인하는 활동.

### 상세 내용

| 구분 | 배포 검증 | 운영 모니터링 |
|---|---|---|
| 확인 시점 | 배포 직후 | 배포 이후 계속 |
| 확인 대상 | 태스크 정의 리비전, 서비스 상태 | 서비스 상태, 성능, 모델 품질 |
| 답하는 질문 | 잘 올라갔는가 | 지금도 제대로 처리하고 있는가 |

- 배포가 끝난 뒤에도 트래픽 증가로 응답 시간이 길어지거나, 컨테이너가 재시작되거나, 입력 데이터 특성이 바뀔 수 있다.
- **배포 검증 기록만으로는 운영 중인 서비스가 계속 정상인지 알 수 없다.** 확인 시점과 대상이 다르므로 두 작업을 따로 수행한다.

**배포 경로가 둘이라는 점이 모니터링에서도 문제가 된다**

- `ml-cicd`와 `ml-deploy`는 **같은 ECS 서비스**를 배포한다. `ml-deploy`는 champion 별칭을 확인하지만 `ml-cicd`는 main push마다 별칭 확인 없이 배포한다.
- 배포 기록에 조건을 남겨도, **현재 서비스가 어느 Workflow로 배포됐는지는 Actions 실행 기록과 ECS 상태를 다시 확인해야만 알 수 있다.**

## 2. 데이터 드리프트와 개념 드리프트

### 핵심 개념

모델은 학습 시점 데이터의 분포를 기준으로 만들어진다. 운영 입력이 그 분포에서 멀어지면 예측 정확도가 낮아질 수 있다. **이 변화는 ECS 상태와 CloudWatch 오류 로그만으로는 확인하기 어렵다.**

### 상세 내용

| 종류 | 정의 | iris 예시 |
|---|---|---|
| **데이터 드리프트(Data Drift)** | 입력 데이터의 분포가 학습 시점과 달라지는 현상 | 운영 요청의 꽃잎·꽃받침 치수 분포가 학습 데이터와 크게 달라짐 |
| **개념 드리프트(Concept Drift)** | 입력과 정답 사이의 **관계**가 달라지는 현상 | 입력 분포는 그대로인데 같은 입력에 대한 정답이 바뀜 |

- 개념 드리프트는 입력 분포가 유지돼도 발생한다. 기존 모델의 판단 기준 자체가 더 이상 맞지 않는 상황이다.
- 어제 ch03-1에서 "평가 데이터와 운영 데이터의 분포가 다르면 테스트를 통과한 모델도 운영에서 성능이 떨어진다"고 배웠는데, 그게 배포 시점의 문제였다면 드리프트는 **시간이 지나면서 생기는** 같은 문제다.

## 3. CloudWatch 로그와 모델 상태 점검

### 핵심 개념

ECS 컨테이너의 표준 출력은 CloudWatch Logs에 저장된다. 로그 그룹·스트림에서 서비스 상태를 확인하고, **추론 로깅**으로 모델 관찰에 필요한 정보를 남긴다.

### 상세 내용

**로그 구조**

- ch02-3의 `task-definition.json`이 `awslogs` 드라이버로 컨테이너 표준 출력을 CloudWatch Logs로 보낸다. 로그 그룹 이름은 `/ecs/devmlops-fastapi`.
- 로그 스트림 이름은 `awslogs-stream-prefix` 값(`ecs`) + 컨테이너 이름 + 태스크 ID 조합.
- **태스크가 재시작될 때마다 새 로그 스트림이 생긴다.** 최근 스트림이 현재 실행 중인 태스크의 로그이고, 이전 스트림에서는 과거 배포와 재시작 시점의 로그를 볼 수 있다.

```bash
aws logs describe-log-groups --log-group-name-prefix /ecs/devmlops-fastapi
aws logs describe-log-streams --log-group-name /ecs/devmlops-fastapi \
  --order-by LastEventTime --descending
```

| 용어 | 의미 |
|---|---|
| 로그 그룹(Log Group) | 서비스나 AWS 리소스의 로그를 모으는 CloudWatch 단위 |
| 로그 스트림(Log Stream) | 로그 그룹 안에서 태스크 하나가 시간 순서대로 남긴 로그 묶음 |

**모델 상태 점검 체크리스트**

로그를 열어도 **점검 기준이 없으면 정상 여부를 판단할 수 없다.** 기본 항목:

| 항목 | 확인 수단 |
|---|---|
| 헬스체크 상태 | `/health` 응답 |
| 응답 시간 | CloudWatch의 uvicorn 접근 로그 |
| 오류율 | 422·503 등 오류 응답 발생 여부 |
| 배포된 모델 버전 | ch03-3에서 기록한 champion 버전·run_id |

- 응답 시간과 오류율은 로그로 확인된다. **하지만 예측 결과가 실제 정답과 맞는지는 로그만으로 알 수 없다.**

**추론 로깅(Inference Logging)**

드리프트나 이상 예측을 조사하려면 `/predict` 요청의 입력 특성과 예측 결과를 애플리케이션 로그에 남겨야 한다.

```python
logger.info(
    "predict request=%s prediction=%s probability=%.4f",
    features.model_dump(),
    prediction,
    probability,
)
```

- **그런데 운영 서비스는 개인정보와 민감한 입력값을 그대로 로그에 남기지 않는다.** 애플리케이션 로그는 CloudWatch에 저장되어 Console과 CLI로 조회 가능하기 때문에, 로그에 남긴 순간 접근 범위가 넓어진다.
- 순서가 중요하다 — **입력값 마스킹 방식과 로그 보관 기간을 먼저 정한 뒤 로깅 범위를 결정한다.**

## 4. Airflow 소개와 다음 학습 로드맵

### 핵심 개념

GitHub Actions는 **이벤트**로 Workflow를 시작한다. 재학습이나 정기 점검처럼 정해진 시간에 반복되는 작업은 **스케줄 기반 오케스트레이션 도구**가 적합하다.

### 상세 내용

| 도구 | 실행 조건 | 적합한 작업 |
|---|---|---|
| GitHub Actions | 이벤트 (커밋 push, `workflow_dispatch`) | 코드 변경에 반응하는 빌드·테스트·배포 |
| Airflow | 스케줄 | 매일 새벽 재학습, 정기 점검처럼 일정 기반 반복 |

- **Airflow**: 작업 의존 관계를 **DAG(Directed Acyclic Graph)**로 정의하고 정해진 일정에 따라 실행하는 워크플로우 오케스트레이션 도구.
- **DAG**: 작업 실행 순서와 의존 관계를 방향이 있는 비순환 그래프로 표현한 구조.
- 예시 DAG: 데이터 수집 → 재학습 → 성능 검증 → Model Registry 등록. 이 순서를 등록해두면 정한 시간에 전체가 실행된다.
- Airflow 서버 구성은 과정 범위 밖. **두 도구가 다른 실행 조건을 다룬다**는 점만 짚는다.
  - `needs`로 job 순서를 만든 것과 DAG는 발상이 닮았다. 차이는 **무엇이 실행을 시작시키는가**에 있다.
