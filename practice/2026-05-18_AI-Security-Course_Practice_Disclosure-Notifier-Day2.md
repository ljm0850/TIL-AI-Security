## 실습 개요

- **목표**: 어제 완성한 기획 산출물(페르소나)을 기반으로 추가 기획(HMW·MVP·PRD·사용자 여정 지도), 실제 Streamlit 웹 개발 착수 및 배포까지 완료
- **방법**: 역할 분리(백엔드/프론트엔드) → 인터페이스 문서 기반 병렬 개발 → 통합 → Streamlit Cloud 배포

## 진행 과정

### Step 1. 기획 산출물 완성 (어제에서 이어짐)

어제 페르소나 2개로 진행하다 기능 복잡도가 높아지는 문제를 인식, 이서연 페르소나를 폐기하고 김재현 단일 페르소나 기준으로 재정리했다.

완성된 산출물 목록:

| 문서 | 내용 요약 |
|---|---|
| 페르소나(상세) | 김재현 (26세, 주식 1년차) — 알림 과다로 중요 공시 놓치는 개인 투자자 |
| HMW | Pain Point 6개 → 기능 아이디어 연결 (Must 4개, Should 2개) |
| MVP 기능 명세서 | F-01 즉시 알림 / F-02 중요도 뱃지 / F-03 유형 필터 (Must 3개) |
| 사용자 여정 지도 | 9단계 여정, 감정 흐름, HMW·기능 연결 |
| PRD | 배경·KPI·범위·시나리오·기능요구사항·MoSCoW·Edge Cases |

**페르소나 폐기 결정의 이유**
MVP인데도 페르소나가 2개면 각 페르소나의 니즈가 충돌하거나 기능이 분산된다. "초보자 용어 해설"(이서연)과 "빠른 필터링"(김재현)은 방향이 달라 하나의 앱에서 동시에 잘 하기 어렵다. 타겟을 좁히는 것이 MVP의 핵심이라고 판단했다.

### Step 2. Git 기초 교육 (팀원 대상)

팀원이 Git 경험이 없어 개발 착수 전 기초 개념을 설명했다.

| 개념 | 설명한 내용 |
|---|---|
| 원격 저장소 | 로컬 코드를 GitHub에 올려두면 팀원 모두가 접근 가능한 공유 공간이 된다 |
| Branch | 기능별로 작업 공간을 분리해 서로의 코드에 영향을 주지 않는 방식 |
| git add / commit / push | 변경사항 스테이징 → 저장 → 원격 반영의 3단계 흐름 |

**협업 방식 결정**
혼자 빠르게 다 만들 수도 있지만 그러면 팀원에게 인공지능사관학교 과정의 의미가 없다고 생각했다. 그래서 AI를 활용해 기능 단위로 역할을 나눴다.

- **나 (백엔드/AI 담당)**: DART 공시 수집, 중요도 분류 로직, AI 1줄 요약 생성, 프론트에 전달할 데이터 구조 정의
- **팀원 (프론트/UX 담당)**: Streamlit UI 구성, 필터·카드 렌더링, 사용자 인터랙션

> Streamlit으로 만드는 앱이라 엄밀한 백/프론트 분리는 아니지만, 팀원이 추후 프로젝트에서 역할 분리와 인터페이스 기반 협업의 개념을 체득하도록 이 방식을 택했다.

### Step 3. 백엔드 모듈 개발 (내 담당)

**개발 방식**: VSCode + Claude Code 활용, 빠르게 완성

**모듈 구조**
```
backend/
├── dart_client.py       # DART API 호출 (또는 샘플 데이터 폴백)
├── llm_classifier.py    # GPT 기반 중요도 분류 + 1줄 요약 + 영향도 판단
└── __init__.py          # get_classified_disclosures() 진입점 노출
```

**핵심 함수**: `get_classified_disclosures(date, importance_rules)`
- DART에서 공시 수집 → GPT로 중요도(`high/mid/low`) + 1줄 요약 + 영향도(`pos/neg/neu`) 분류
- 결과를 `list[dict]` 형태로 반환 → 프론트에서 필터링·렌더링에 바로 사용 가능

**코드 완성 후 리팩토링**
완성 직후 코드를 검토하니 중요도 분류 기준이 하드코딩되어 있었다. 사용자가 필터를 바꿀 때마다 코드를 수정해야 하는 구조였다. `importance_rules` 파라미터를 추가해 프론트에서 동적으로 기준을 주입할 수 있도록 수정했다.

**문서화**
- `B 모듈 인터페이스 문서 v1.1` → 팀원(프론트)이 내 모듈을 import해서 쓸 수 있도록 함수 명세·반환값 구조 정의
- `Backend API 명세서 v1.0` → 엄밀히 API는 아니지만, 추후 프로젝트에서 팀원이 API 명세서 개념을 익히도록 의도적으로 작성

**예외 처리 설계**

| 상황 | 동작 |
|---|---|
| DART API 호출 실패 | 샘플 데이터로 폴백, 콘솔 경고 |
| GPT 호출 실패 / 응답 None | `importance="low"`, `summary="요약 실패"`, `sentiment="neu"` 기본값 처리 |
| 해당 날짜 공시 없음 | 빈 리스트 `[]` 반환 |

### Step 4. 팀원 개발 지원

팀원이 프론트 개발 중 마주친 문제들을 지원했다.

| 이슈 | 원인 | 해결 |
|---|---|---|
| ChatGPT 사용 중 코드 생성 어려움 | ChatGPT 웹을 이용하여 코드 작성 | OpenAI CODEX 모델 안내 |
| `IndentationError` | Python 들여쓰기 오류 | 4칸 스페이스 기준 직접 수정 |
| API 호출 에러 | `.streamlit/secrets.toml`에 API 키 미입력 | secrets.toml 작성법 안내 |
| 코드 수정 후 화면이 안 바뀜 | 로컬 서버 캐시 문제 (핫 리로드 미반영) | 서버 재시작으로 해결 |

## 느낀 것 / 배운 것

- 페르소나를 줄이는 결정이 단순히 작업량을 줄이는 게 아니라 제품의 방향을 명확히 하는 행위라는 걸 체감했다. "초보자 해설"과 "빠른 필터링"은 같은 앱에서 동시에 잘 하기 어렵다.
- 인터페이스 문서를 먼저 쓰고 개발하니 팀원이 내 코드를 기다리지 않고 UI를 먼저 짤 수 있었다. 문서가 계약서 역할을 한다는 걸 실감했다.
- Claude Code로 코드를 빠르게 뽑은 뒤 직접 검토하는 과정에서 하드코딩 문제를 잡아냈다. AI가 만든 코드를 그냥 쓰지 않고 리뷰하는 습관이 중요하다.
- "팀원이 직접 해봐야 의미가 있다"는 판단으로 분리한 역할이 실제로 팀원의 학습에 기여했다. Git, secrets.toml, 서버 재시작 등 작은 경험들이 쌓이는 걸 옆에서 봤다.
- API 명세서라는 명칭을 의도적으로 쓴 건 잘한 선택 같다. 엄밀하지 않더라도 개념을 먼저 심어두는 게 나중에 실제 API를 만날 때 훨씬 빠른 이해로 이어질 것이다.
