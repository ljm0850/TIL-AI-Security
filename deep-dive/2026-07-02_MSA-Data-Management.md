## 왜 찾아봤는가
과거 프로젝트에서 팀원들이 MSA를 시도했을 때 "서비스마다 DB를 나눠야 하는가, 공통으로 쓰는 데이터(회원 정보 등)는 어떻게 처리하는가"에 대해 많은 고민을 하였다. 오늘 AWS VPC를 배우면서 같은 의문이 다시 떠올라 정리했다.

## 핵심 내용

### 기본 원칙 — Database per Service
MSA에서는 서비스마다 자기만의 DB를 갖는 게 기본 패턴이다.
- 서비스는 자기 DB에만 직접 접근
- 다른 서비스의 데이터가 필요하면 반드시 **API 또는 이벤트**를 통해서만 접근 (DB 직접 조회 금지)

DB를 공유하면: 스키마 변경이 여러 서비스에 동시 영향, 독립 배포 불가능, MSA의 의미 퇴색.

### 공통 데이터 처리 패턴 4종

**1. API 호출 (동기)**
- 필요할 때 다른 서비스 API 호출
- 장점: 항상 최신 데이터, 구현 단순
- 단점: 대상 서비스 장애 시 같이 영향받음(장애 전파), 호출 많아지면 느림

**2. 이벤트 기반 복제 (비동기) — 가장 많이 쓰임**

- 데이터 변경 시 Kafka/RabbitMQ 등에 이벤트 발행, 필요한 서비스가 구독해서 자기 DB에 필요한 필드만 복제
- 장점: 조회 시 다른 서비스 호출 불필요, 결합도 낮음
- 단점: Eventual consistency — 변경 직후 짧은 시간 동안 서비스 간 데이터 불일치 가능

**3. CQRS**
- 여러 서비스 데이터를 이벤트로 받아 미리 합쳐 놓은 조회 전용 read model/DB를 별도로 둠
- 대시보드·통합 검색처럼 여러 도메인 데이터를 한 번에 보여줄 때 유용

**4. Saga 패턴**
- 여러 서비스에 걸친 트랜잭션(주문→재고→결제)을 이벤트로 이어붙이고, 실패 시 보상 트랜잭션으로 롤백
- 분산 트랜잭션 대신 "각 단계가 실패하면 이전 단계를 되돌리는 이벤트를 발행"하는 방식

### 비교 요약

| 방식 | 일관성 | 결합도 | 적합한 상황 |
|---|---|---|---|
| API 호출 (동기) | 강한 일관성 | 높음 | 실시간 최신 데이터가 꼭 필요할 때 |
| 이벤트 기반 복제 (비동기) | 최종적 일관성 | 낮음 | 대부분의 조회성 데이터 공유 |
| CQRS | 최종적 일관성 | 낮음 | 여러 도메인 합친 조회/대시보드 |
| Saga | 보상 기반 | 중간 | 여러 서비스에 걸친 트랜잭션 |

### AWS VPC와의 연결
MSA에서 각 서비스 서버 간 통신은 VPC 안의 사설 IP로 처리 가능하다. 회원 DB 서버를 외부에 노출하지 않으려면 — 보안 그룹으로 내부 서비스 서버의 사설 IP에서 오는 요청만 허용. 이벤트 기반 복제에서 사용하는 메시지 브로커(Kafka 등)도 VPC 내부에서만 접근 가능하게 구성하는 게 표준.

## 이해한 것 / 아직 모르는 것

| 이해한 것 | 아직 모르는 것 |
|---|---|
| Database per Service가 기본 원칙인 이유 (독립 배포, 결합도) | Kafka 같은 메시지 브로커를 AWS에서 실제로 어떻게 구성하는지 (MSK 등) |
| 이벤트 기반 복제가 기본 패턴인 이유 (결합도 낮음, 장애 격리) | Eventual consistency가 허용되지 않는 케이스에서 Saga 패턴의 구체적 구현 |
| VPC 사설 IP로 서비스 간 내부 통신 격리 가능 | |
