# 닐슨 휴리스틱을 실제 서비스 평가에 적용하기
## — 취업준비생용 RAG 서비스 실전 가이드 (취업준비생 시나리오)

> **작성 맥락**: 인공지능사관학교 AI 보안 트랙 1주차 학습 내용(닐슨 10가지 사용성 휴리스틱)을 실제 토이프로젝트에 적용하기 위해 deep-dive한 내용을 정리한 문서.
> **대상 서비스**: GitHub 데이터 기반 개인 RAG 서비스 (자소서 작성 보조 + 채용담당자 접근 기능)
> **이 문서의 범위**: 취업준비생(나) 시나리오

---

## 핵심 사용 흐름

```
자소서 작성 중 곤란한 질문 발생
        ↓
RAG 서비스 접속
        ↓
회사/직무 정보 입력 + 자소서 질문 입력
        ↓
GitHub 데이터 기반 RAG 답변 생성
        ↓
답변을 참고해서 자소서 작성
```

---

## 단계별 휴리스틱 적용

### 단계 1: RAG 서비스 접속

자소서를 쓰다가 막혔을 때 접속하는 상황. 스트레스를 받는 상태에서 진입하는 만큼 인지 부하를 최소화해야 한다.

| 휴리스틱 | 설계 포인트 | MVP 여부 |
|---|---|---|
| 기억보다 인지 | 입력창 placeholder로 사용법 힌트 제공 (예: "자소서 질문을 붙여넣으세요") | MVP |
| 미니멀리즘 | 핵심 기능(질문 입력)만 전면 배치, 부가 기능은 숨기기 | MVP |

---

### 단계 2: 질문 입력

자소서 질문과 회사/직무 정보는 성격이 다른 입력이므로 분리해서 설계해야 한다.

#### 2-1. 입력 구조 설계

```
단계 2-1: 회사/직무 정보 입력 (컨텍스트 설정)
        ↓
단계 2-2: 자소서 질문 입력
        ↓
단계 2-3: 입력 검증 후 API 요청
```

**회사/직무 정보 분리의 이유**
- **시스템과 실제 세계의 일치**: 사용자 입장에서 두 입력은 명확히 다른 정보. 하나의 입력창에 섞이면 인지적으로 어색함
- **오류 방지**: 분리 구조 자체가 회사 정보 없이 질문만 보내는 실수를 막음

#### 2-2. 회사 정보 저장 정책

취업 준비는 여러 회사에 동시 지원하며 며칠씩 진행되므로 회사 정보 저장이 필요하다. 단, 불합격한 회사 정보가 목록에 남으면 사용자 경험에 부정적 영향을 줄 수 있다.

| 방식 | 장점 | 단점 | 우선순위 |
|---|---|---|---|
| 저장 + 삭제 | 간단한 구현 | 실수로 삭제 시 복구 불가 | MVP |
| 아카이브 (숨김 처리) | 감정적으로 안 보임, 복구 가능 | UI 복잡도 증가 | 고도화 |
| 상태 태그 (지원중/합격/불합격) | 현황 관리 가능 | 불합격 태그 달기 싫을 수 있음 | 고도화 |

#### 2-3. 입력 검증

| 휴리스틱 | 설계 포인트 | 구현 방법 | MVP 여부 |
|---|---|---|---|
| 오류 방지 | 질문이 너무 짧을 때 경고 | text length 기준 경고 | MVP |
| 오류 방지 | 질문이 모호할 때 가이드 제공 | LLM 사전 검토 | 고도화 |
| 시스템과 실제 세계의 일치 | 친숙한 언어 사용 | "쿼리 입력" → "자소서 질문을 입력하세요" | MVP |
| 유연성과 효율성 | 자주 쓰는 질문 템플릿 저장 | 템플릿 저장/불러오기 기능 | 고도화 |

---

### 단계 3: RAG 답변 생성 중 (대기)

사용자가 아무것도 할 수 없는 수동적 대기 구간. RAG 특성상 일반 검색보다 응답 시간이 길 수 있어 피드백이 중요하다.

| 휴리스틱 | 설계 포인트 | MVP 여부 |
|---|---|---|
| 시스템 상태의 가시성 | 로딩 중임을 명확히 표시 | MVP |
| 사용자 제어 및 자유 | 생성 중 취소 버튼 제공 | MVP |

#### 로딩 피드백 고도화 로드맵

| 단계 | 방식 | 효과 |
|---|---|---|
| MVP | 단순 스피너 | 최소한의 피드백 |
| 고도화 v1 | 텍스트 피드백 ("GitHub 데이터 검색 중..." → "답변 생성 중...") | 진행 단계가 보임 |
| 고도화 v2 | 스트리밍 출력 (ChatGPT 방식) | 대기감 거의 없음 |

---

### 단계 4: 답변 확인

서비스의 핵심 가치가 전달되는 순간. 답변의 신뢰도가 가장 중요하다.

#### RAG 신뢰도 문제

GitHub 데이터 기반 RAG는 두 가지 이유로 잘못된 답변을 줄 수 있다.

1. **데이터 해석 오류**: md 파일 변환 과정에서 맥락이 왜곡될 수 있음
2. **미완성 섹션 혼동**: "추가로 학습할 것"을 "이미 학습한 것"으로 오해할 수 있음

**해결 방법 — md 파일 양식 개선**

```markdown
## 학습 완료
- 트랜스포머 아키텍처
- LLM 취약점 분류

## 추가로 학습할 것 (미완료)
- 방어기법
```

완료/미완료를 명시적으로 구분하면 RAG의 혼동 여지를 제거할 수 있다.

| 휴리스틱 | 설계 포인트 | MVP 여부 |
|---|---|---|
| 오류 인식 및 복구 지원 | 관련 데이터 못 찾았을 때 이유 명시 + 질문 수정 유도 | MVP |
| 기억보다 인지 | 어떤 md 파일을 참고했는지 출처 표시 | MVP |
| 사용자 제어 및 자유 | 답변 재생성 버튼, 질문 수정 버튼 | MVP |

---

### 단계 5: 답변을 참고해서 자소서 작성

서비스 밖으로 나가는 순간. 실제 자소서 작성 패턴을 반영한 설계가 필요하다.

#### 실제 사용 패턴

```
RAG 답변 받음
        ↓
내 언어로 손봄
        ↓
AI(Claude 등)에게 다시 개선 요청
        ↓
반복
```

이 패턴에서는 이전 RAG 답변을 다시 볼 필요가 없다. **답변 복사 버튼** 하나가 핵심이다.

| 휴리스틱 | 설계 포인트 | MVP 여부 |
|---|---|---|
| 유연성과 효율성 | 답변 복사 버튼 | MVP |
| 미니멀리즘 | 답변 외 불필요한 UI 최소화 | MVP |
| 유연성과 효율성 | 이전 답변 히스토리 조회 (회사별) | 낮음 |
| 사용자 제어 및 자유 | 같은 질문에 대한 여러 답변 비교 | 고도화 |
