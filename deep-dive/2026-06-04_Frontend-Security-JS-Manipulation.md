> **작성 계기**: JavaScript 소스코드가 브라우저에 그대로 노출된다는 점에서 프론트엔드 조작 공격을 찾아봄. 이전에는 함수 인자 조작 정도만 생각했는데, 범위가 훨씬 넓었다.

---

## 왜 찾아봤는가

강의 중 "JS 소스코드는 브라우저에 그대로 전달된다"는 내용을 듣고, 프론트엔드 보안에 대해 다시 생각하게 됐다. 예전에는 API 요청 시 인자 값을 바꾸는 수준만 생각했는데, DevTools로 JS 자체를 수정하거나 API를 직접 호출하는 방법까지 있다는 걸 인식하고 구체적인 공격 유형과 방어 방법을 정리했다.

---

## 핵심 내용

### 1. 공격의 전제 — 프론트엔드는 믿을 수 없다

브라우저 DevTools로 JS 소스를 열람·수정할 수 있기 때문에, **클라이언트에서 수행하는 모든 검증과 제한은 공격자에게 노출**된다.

| 공격 유형 | 방법 | 영향 |
|---|---|---|
| 인자 조작 | 요청 파라미터 직접 수정 | 가격·userId 위조 |
| 검증 우회 | 조건문 비활성화 | 입력 제한 무력화 |
| 토큰 탈취 | localStorage 접근 | 세션 도용 |
| 비즈니스 로직 우회 | API 직접 호출 | 결제·권한 체크 스킵 |

---

### 2. 비즈니스 로직 우회 공격

**케이스 1 — 결제 가격 조작**

DevTools로 요청 파라미터의 `price`를 1원으로 바꿔서 전송. 서버가 클라이언트가 보낸 가격을 그대로 사용하면 1원 결제가 성립한다.

방어: 서버에서 `productId`로 DB를 재조회해 가격을 결정. 클라이언트의 `price`는 무시.

```javascript
// 취약한 코드
app.post('/order', (req, res) => {
    const { productId, price } = req.body; // price 신뢰 금지
    db.createOrder({ productId, price });
});

// 방어 코드
app.post('/order', async (req, res) => {
    const { productId } = req.body;
    const product = await db.getProduct(productId);
    db.createOrder({ productId, price: product.price }); // DB 값 사용
});
```

**케이스 2 — 쿠폰 중복 사용 (Race Condition)**

100ms 안에 동일 요청 10개를 동시 발송. 서버가 모두 "미사용" 상태로 확인하면 쿠폰 10회 적용.

단순 중복 체크로는 막을 수 없다. 확인(check)과 처리(act) 사이의 간격이 공격 표면이다.

방어: `UPDATE ... WHERE used = 0` — 조건부 UPDATE를 원자적으로 실행. 영향받은 행이 0이면 이미 사용된 것.

**케이스 3 — 재고 음수**

`quantity: 9999` 파라미터 전송 → 재고 = 1 - 9999 = -9998

방어: `UPDATE products SET stock = stock - :qty WHERE id = :id AND stock >= :qty` 한 쿼리로 검증과 차감을 원자적 처리.

**케이스 4 — 등급/권한 우회**

요청 바디에 `role: "admin"` 주입. 서버가 이를 신뢰하면 관리자 권한 획득.

방어: `role`은 반드시 서버가 서명한 JWT payload에서만 추출.

### 3. API 직접 호출 공격

프론트엔드를 완전히 건너뛰고 `curl`, Postman 등으로 API를 직접 호출. 프론트가 제공하는 모든 제약이 사라진다.

**Rate Limit 우회**: 버튼 비활성화나 입력 횟수 제한은 UI 로직이라 직접 호출 시 무의미. 로그인 브루트포스 가능.

방어: IP·토큰 기반 서버 Rate limit (Redis 등)

**내부 엔드포인트 탐색**: JS 번들 분석으로 화면에 노출되지 않는 관리 API 경로 발견 가능.

방어: 모든 엔드포인트에 인증 미들웨어 적용. "버튼이 없으니 안전하다"는 착각 금지.

**파라미터 퍼징 (IDOR 자동화)**: `id=1`부터 자동으로 올려가며 타인 데이터를 대량 수집.

방어: 소유권 검증 + 에러 메시지 일반화 (404 반환으로 존재 여부도 숨김)

**탈취 토큰 재사용**: XSS나 네트워크 스니핑으로 JWT 탈취 후 그대로 사용.

방어: Access token 만료 시간 짧게 (15분), 이상 접근 패턴 감지

---

### 4. 공통 방어 원칙 — Never Trust the Client

| 항목 | 잘못된 접근 | 올바른 접근 |
|---|---|---|
| 가격·수량 | 클라이언트 전달값 사용 | 서버 DB에서 재조회 |
| 권한(role) | 요청 파라미터에서 읽음 | JWT payload에서만 추출 |
| 입력 검증 | 프론트에서만 검증 | 서버에서 타입·범위 재검증 |
| 재고 차감 | check → act 분리 | 원자적 SQL 한 쿼리 |
| Rate limit | 버튼 비활성화 | 서버 IP/토큰 기준 제한 |

**API 서버는 항상 "브라우저 없이 호출된다"는 가정으로 설계한다. 프론트가 걸러줄 거라는 기대 자체가 취약점이다.**

## 이해한 것 / 아직 모르는 것

| 이해한 것 | 아직 모르는 것 |
|---|---|
| 클라이언트 검증은 UX용, 보안은 서버에서 | XSS로 JWT를 탈취하는 구체적인 방법 |
| Race Condition이 왜 단순 중복 체크로 막히지 않는지 | CSRF 공격과의 차이점 |
| 원자적 SQL 연산으로 Race Condition 방어하는 원리 | API Rate limiting 서버 구현 상세 |
| IDOR 공격의 자동화 원리 | CSP(Content Security Policy)가 실제로 막는 범위 |
