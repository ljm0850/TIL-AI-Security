## 왜 찾아봤는가

강의에서 VPC, 서브넷, 라우팅 테이블, NAT 게이트웨이 개념이 빠르게 지나갔는데 MSA 구조와 어떻게 연결되는지 이해가 안 됐다. 특히 "프라이빗 서브넷에 있는 서비스끼리는 어떻게 통신하고, IP가 계속 바뀌는 환경에서 서로를 어떻게 찾는가"가 핵심 의문이었다.

---

## 핵심 내용

### VPC란
AWS 클라우드 안에 내가 소유하는 독립된 가상 네트워크 공간. CIDR 블록으로 IP 대역을 직접 지정하고 내부를 서브넷으로 나눠 구조를 설계한다. EC2, RDS 같은 리소스는 반드시 어떤 VPC 안에 위치해야 동작한다.

### MSA 구조에서 서브넷 설계

VPC가 공개/비공개를 결정하는 게 아니라, **서브넷에 연결된 라우팅 테이블에 인터넷 게이트웨이(IGW) 규칙이 있는지 여부**가 퍼블릭/프라이빗을 결정한다.

```
VPC (10.0.0.0/16)
├── 퍼블릭 서브넷 (10.0.1.0/24)
│   └── ALB, API Gateway 등
│       → IGW 연결, 외부 인터넷과 통신 가능
│
└── 프라이빗 서브넷 (10.0.2.0/24)
    ├── 주문/결제/유저 서비스 EC2
    └── DB (RDS)
        → 외부에서 직접 접근 불가, VPC 내부에서만 통신
```

**트래픽 흐름**: 외부 요청 → 퍼블릭 서브넷 ALB → 프라이빗 서브넷 내부 서비스 → DB

### CIDR

| CIDR | 사용 가능한 IP 수 |
|---|---|
| `10.0.0.0/16` (VPC 전체) | 약 65,536개 |
| `10.0.1.0/24` (서브넷) | 256개 |

`/` 뒤 숫자가 작을수록 IP 대역이 넓다. VPC에 큰 대역을 할당하고 서브넷 단위로 쪼개 쓴다.

### 라우팅 테이블

| 서브넷 | 목적지 | 대상 |
|---|---|---|
| 퍼블릭 | `0.0.0.0/0` | Internet Gateway |
| 프라이빗 | `0.0.0.0/0` | NAT Gateway (아웃바운드만) |

NAT 게이트웨이: 프라이빗 서브넷 → 인터넷 단방향. 나가는 요청은 허용, 들어오는 요청은 차단.

### 마이크로서비스 간 통신 — 서비스 디스커버리

인스턴스가 뜨고 죽으면서 IP가 계속 바뀌는 MSA 환경에서 IP 하드코딩은 불가능하다. 서비스 디스커버리가 필요한 이유.

| 방식 | 설명 | 적합한 시점 |
|---|---|---|
| 내부 ALB | 서비스마다 내부용 로드밸런서 + 고정 DNS | MSA 초기 단계 (추천) |
| AWS Cloud Map | 자동 등록 레지스트리, 내부 DNS 조회 | ECS/EKS 사용 시 |
| 서비스 메시 (App Mesh) | 디스커버리 + 재시도 + 서킷브레이커 | 서비스 10개 이상 |

**실무 팁**: 초기에는 내부 ALB 방식이 설정 단순하고 관리하기 쉽다.

## 이해한 것 / 아직 모르는 것

| 이해한 것 | 아직 모르는 것 |
|---|---|
| 서브넷의 퍼블릭/프라이빗은 라우팅 테이블의 IGW 규칙 유무로 결정 | 보안 그룹으로 "A 서비스만 B 서비스 호출 가능"하게 제한하는 구체적 설정 |
| NAT 게이트웨이가 프라이빗 서브넷의 단방향 아웃바운드를 담당 | 내부 ALB 실제 설정 방법 (콘솔에서 직접 해보지 않음) |
| MSA 초기엔 내부 ALB 방식이 단순하고 적합 | Cloud Map과 내부 ALB를 언제 전환하는 게 적절한지 기준 |
